# cfg 身份普查：4,780 个匿名条目拿到真路径，但**不能**喂给动画线（2026-10-11）

工具：`cargo run --bin cfg_named`（`crates/core/src/bin/cfg_named.rs`，只读；给 `--out=` 才落盘）。
原理一句话：引擎的 pak 索引哈希就是 `path_hash(原始全路径)`，把 `ResourcePath.cfg` 的
72,764 条「裸名→全路径」逐条代进去，就能问出「这个匿名包内条目到底有没有路径身份」。

pu 223 · scene 6 · terraininfo 4`。**贴图 0 条。**

骨头各站各的位置，蒙皮就把同一张网格按 83 套**互相错位**的刚体拉。
所以这族接下来的堵点很具体：**父骨链 + 那 20 根的骨位**（`rest.rs` 那套静态区反解只到平移）。

第一版探针把 `skeleton` 当列表遍历，直接 `TypeError` 崩了；这份脚本已改。
挂点表这条路**只否掉了 machao 这一份**，别写成一族都没有（22 份「连节点记录都没有」的那批另有分法）。

## 又自我纠正一次：上一条「补骨位最多修 8.8%」**算漏了子树传导**（2026-10-12）

`__tearPairs` 加了第二个口径：一根**没有绑定记录**的骨，它的骨位错会**连带整棵子树**一起错，
所以不能只看撕边的两个端点自己有没有记录。分类器走 `bone.parent` 链（traverse 是前序，父先分好）。

machao `behit01` 八帧、10,084 条过 2 倍的边：

| 口径 | 数 | 占比 |
| --- | --- | --- |
| 端点**自己**有 96B 记录（上一条用的就是这条） | 9,194 | 91.2% |
| 端点**自己**无记录 | 890 | 8.8% |
| **两端都落在「祖上有无记录骨」的脏子树里**（把 `000` 摘掉再算，见下） | 9,194 | 91.2% |
| **一端落在脏子树里** | 890 | 8.8% |
| ⇒ **落在脏子树里的（任一端）= 9,194 + 890** | **10,084** | **100%** |

**所以「最多只能修 8.8%」这句是错的，方向反了**：撕边**一条不落**地都碰到
「祖上缺绑定记录」的骨（pelvis / spine / spine1 / head 这条躯干主链之下的一切）。
正确的说法是：**补骨位的影响面在 8.8%（端点自己直接受益）到 100%（子树被连带修正）之间**，
上限能不能兑现，只能真补一遍再量，不能靠分类器说。

两个如实的保留：① `000` 是那根占位/根骨。把它当「无记录」时它下面**全是脏子树**，
100% 是恒真的、没信息量——上面这组数取的是**把 `000` 摘掉**那一版，
所以「100%」不是靠根骨兜出来的。② 「碰到脏子树」是**必要条件不是充分条件**：
补上主链骨位以后，那些边可能仍因别的原因撕。要定死，得做下面这个实验。

**实验已经排好（下一件就做这个）**：`bind_worlds` 现在让无记录的骨**与父骨重合**；
把这条换成「按 `.ani` 轨道在第 0 帧的位移给那 18 根补平移、并让它**不带着子树走**」做不到，
但可以做**对照**：把 21 根无记录骨从调色板里**剔掉**（它们的权重挪给最近的有记录祖先），
再拿 `__tearPairs` / `stretch_census` 量一次。
撕塌下去 ⇒ 主因就是它们；纹丝不动 ⇒ 脏子树只是相关不是因果，父骨链另有账。

## 实验跑完：那 19 根无记录的骨**一个顶点都不吃**，前两条百分比一起作废（2026-10-12）

因果实验（`__dropAndMeasure`：把这些骨的权重挪给最近的有记录祖先，再用同一把尺 `__stretch` 量）
第一次跑出来「挪走槽位 0」，我没放过它，往下查，查出一个**我自己的读数 bug**：

**`__tearPairs` 里的 `primary()` 用 `sidx.getX(i, k)` 取槽位 k 的关节——但 three.js 的 `getX` 永远只读第一个分量**，
于是它拿**槽 0 的骨名**去配**槽 k 的权重**。改成 `getComponent(i, k)` 之后数字全变了。
（`__stretch` 用的是 `getX(ix, 0)`，显式槽 0，不受这个 bug 影响。）

改完 + 加自查 `__jointDiag` 之后，machao 的事实是：

| 项 | 实测 |
| --- | --- |
| 骨架骨数 / 被顶点引用的关节数 | 83 / **61**（JOINTS 值域 0..81） |
| 19 根无记录骨被引用的顶点数 | **0** |
| 落在这些骨上的权重合计 | **0.0**（两份 SkinnedMesh 各自都是 0） |
| 撕边两端「自己都有记录」的占比 | **10,084 / 10,084 = 100%**（修正后） |
| 挪走它们的权重后再量 | **一条边都没变**（1086→1086、65.35→65.35…） |

**三条要撤回与一条要立住**：
1. 撤回「补那 20 根的骨位最多修 **8.8%**」——那个 8.8% 是 `getX` bug 造出来的，真实数是 **0%**：
   这些骨根本不在这份网格的蒙皮里，补不补对撕**毫无影响**。
2. 撤回上一条的「撕边 **100% 落在脏子树**」——分类里那 890 条「一端无记录」也是同一个 bug 的产物，
   而「脏子树」这个口径本身也不该拿来当因果：没权重的骨带不动顶点。
3. 立住：**100% 的撕边两端都是「有 96B 记录且真的吃了权重」的骨**。配上
   83/83 调色板全刚体、48 组全局轴置换一组都不救、以及这条新的「无记录骨零权重」——
   撕的成因只剩一处：**这些有记录的骨，彼此之间的变换合成方式错了**（父骨链 / bind 复合），
   不是骨位缺失、不是权重缺失、不是基向量约定。
4. 顺带一个新缺口：**83 根骨里只有 61 根真的被顶点引用**，另外 22 根（含那 19 根无记录的）
   对这份网格是纯装饰。之前把「无记录」当问题面，本来就是打错靶子。

工具与原文：`__dropAndMeasure` / `__jointDiag`（`.scratch/glb_ext/view.html`）、
驱动 `.scratch/glb_ext/drive_drop_missing.mjs`、`diag_joints.mjs`。
教训一条：**读数 bug 会让两个方向的结论都错**——这次先写实验再写结论，
实验跑出「什么都没挪动」才把 bug 揪出来；下次分类器一律配一个「挪动数应为非零」的自检。

## 上一条「节点 rest 塌、IBM 才是对的」**撤回**：是我的算法错了，不是导出器的错（2026-10-12）

方法学这条也值得记：**比两个来源是否一致，要比到 1e-6，别比到「看起来不一样」**——

## 三条都收口：链是数据原文、拓扑排名不是判据、那条「62/63 不等」是我的乘序错（2026-10-12）

**① 父骨链没有编造。** `geometry.rs:1226-1239` 的建树纪律是硬的：
每个非根条目**必须恰好被列进某一条目的孩子名单一次**，孩子名对不上条目就报
「孩子名单里有对不上条目的名字」、被列两次就报「有孩子被列了两次」，多根/有环/条目数≠声明数/不落在 EOF 都整体作废。
**没有"没被列出的骨挂到根上"这种兜底**。我一开始看字节觉得
`bip01_prop1 / bip01_r_clavicle / bone11` 只出现 3 次、"没被当 Child 列过"——那是我没记住
**孩子槽与 96B 记录共用字节**（`geometry.rs:615-617`：有矩阵的骨，孩子槽就是整条 96B 记录，名字段即孩子名）。
所以那 3 处里的记录出现，本身就是它父亲的名单槽。链是原文。

**② 拓扑排名这个问法本身不是判据。** 父亲本来不必是最近的骨（相邻手指、`bone*` 镜像串天然更近），
所以「父亲=最近名次的骨只有 7/44」不能推任何东西。数字留着当描述，**别再拿它当证据**。

**③ 上一轮那条吓人的「合成世界反推的局部 ≠ 轨道 TRS，62/63 根对不上、平移差均值 1.12」作废——是我的乘序错。**
`compose_worlds`（`pose::pose_frame` 用的那个）写的是 `worlds[i] = mat_mul(local[i], worlds[parent])`，
即**行向量约定**下 `W_i = local_i · W_parent`。
要从世界反推局部应当是 `local_i = W_i · W_parent⁻¹`（**右**乘逆），

按正确的乘序它就是恒等式，问不出东西，这一段已从探针里换掉（现在只剩拓扑体检那条臂）。

**这条线到此的净结论**：能在这台机器上排除的都排完了——
轴向/手性、调色板带缩放、无记录骨骨位（零权重）、无轨道骨（零权重）、四槽截断（丢 0.0）、
表分块（无第二块）、名字↔表整体配对（49.8% 排第 1，非随机）、父骨链编造（纪律不允许）、
以及我自己的两处探针算法错（节点 TRS 组合漏祖先旋转、链检查乘序错）。
剩下能定这件事的只剩**引擎在运行时怎么用这些轨道值**——那是要你点头起客户端挂钩的那件事。

## 2026-10-12（第十一补）那 5 份的记录语法**解出来了**：是第三种文法（矩阵每行前置一个 pad、基向量带 100 倍、影响表按顶点）

```
+0   char[32] 骨名
+32  char[32] 同一个骨名再一遍        ← 名字出现两次、相隔 32，全文件 49 次如此
+64  4 × ( f32 0.0 + 3 × f32 )       ← 矩阵：每行前面 pad 一个 0
       行1 (0, 38.33, -92.362, ~0)      三行基向量**长度都是 100**、两两垂直
       行2 (0, ~0, ~0, 100)
       行3 (0, -92.362, -38.33, ~0)
       行4 (0, -53, ~0, -1.6988)   ← 平移
+128 u32 4 · u32 id[4] = 98,96,97,99 · f32 w[4] = 1,1,1,1   ← 影响表：条数 + id + 权重
```

三点与已知文法不同，每一条都有两份记录互证：
1. **名字重复两遍**（我们的记录是「名字 + 紧跟矩阵」）；
2. **矩阵每行前置一个 pad 浮点**，且**基向量长度是 100 不是 1**（单位差 100 倍？还是刻意放大？）——

3. **影响表按顶点组织**（一个顶点带 4 个骨号 + 4 个权重），而全库其余文件是**按骨稀疏存**
