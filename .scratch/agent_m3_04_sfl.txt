[Q1] .sfl 是不是「格子坐标 -> .scene 文件」的索引表？  —— 答案：否
------------------------------------------------------------------------------
扫描 297 个 .sfl 的全部字符串，共 12730 条：
  以 .scene 结尾        : 0   <-- 反例数为 0，即一个都不引用
  a_b_c 坐标形状的字符串 : 0   <-- 反例数为 0

  交叉证据（命名关系，反过来说明二者是"同级同名"而非"索引"关系）：
    - 297 个 .sfl 中 292 个的文件名 == 同目录某 .scene 的主名：
        mobile_maps/<地图ID>/<地图ID>.sfl  <->  .../<地图ID>.scene
    - 只有 1 个目录的 .scene 全部是 a_b_c.scene 网格命名；
      其余目录的 .scene 叫 <地图ID>.scene（如 w1351_fb_migong_shamo_001.scene）。
    - 参考：目录里带坐标的网格名形如 1_-1717_-2645.scene，共 218 个不同名，
      全部挂在同一个目录下（x 恒为 1），与 .sfl 的 297 个文件无从一一对应。

  结论：.sfl 不含任何 .scene 引用、不含任何坐标串。它不是格子索引表。
        .sfl 是"每张地图一份"的**场景光照/天空/雾**配置文件。

[Q4] .sfl 的规模是否与地图的格子数相关？  —— 答案：不相关
------------------------------------------------------------------------------
  有 .sfl 的地图数: 296（其中 1 张另有 _high 变体）
  .sfl 字节数 vs 同目录 .scene 个数：
    格子数 min 1 max 133   .sfl 字节 min 600 max 11184   Pearson r = 0.286
    同样的格子数 -> 同样的 .sfl 大小吗？
      按格子数分桶 82 个，其中"同桶内大小还不唯一"的有 46 个（56%）
      例：2 个格子的地图，.sfl 大小可能是 [3600, 2472, 5744, 5744, 6560, 9056]
      例：65 个格子的地图，.sfl 大小可能是 [1128, 1144, 10224, 9440, 9440, 10936, 10936, 2680]

  结论：r=0.29（弱相关），且同格子数的地图之间大小差异达 4 倍以上。
        .sfl 是"白天/黑夜光照配置"，只跟美术需要几套光照曲线有关，
        跟地图由几个格子拼成无关。
        反证：mob+high 变体 mqts_empty_001（2 个格子）就有 3600 字节，
              而 w1351_fb_jhqx_001（也是极少格子）只有 600 字节。

[6] 未解清单（哪些字节没读懂）
------------------------------------------------------------------------------

  U1. u32@20 的语义。值域 556..4920，与 strtab 偏移恒差 24（287 例）或 28（10 例）。
      实验排除：它不是 id-85 块的偏移（0/297 命中）；不是 strtab 偏移（0/297）；
      不是任何提前的块偏移。候选解释：某块的 size（差 24 = 块头+对齐），
      或一个 hmm 无关的填充。反证方法：找到差值非 24/28 的文件。
  U2. 偏移 24..52 的 8 个 u32 的语义。已知：
        @24 = 77 (0x4D) 恒等全部 297 个文件；
        @28 = @32 = 0；
        @36 = 3 (289 例) / 2 (8 例)；
        @40 = 一个 127..1219 的整数，且与文件大小正相关（不是文件大小、不是格子数）；
        @44 = 39 恒等；
        @48 = 9/10/12/13/19/24，@52 = 38/41/44/46/78/80，两者一一配对，
              数值与 @40 同量级 → 强烈推测 @40/@48/@52 是三个长度或计数。
  U3. 偏移 24 起的**记录流切分规则未解**。已试过的假设全部失败（可复现）：
        假设A「[cnt][attr] + cnt*u32，步长 12/8/16」：0/297 能走到 strtab 前；
              且"计数"字段会退化成 1，即该假设不成立。
        假设B「tag<<24|id 单字头 + 定长参数」：能走完全程但落点不唯一，无法作为切分。
      已知记录在文件中**不是按字段顺序排列**：
        600B 样本里 attr 出现的先后是 69,68,168,34,71,73,74,172,173；
        而字符串块里字段名顺序是 69,68,168,34,71,73,74,172,173,...,40。
        对不上完整字段集 → 说明参数区还夹着变长（关键帧串）负载。
      未能给出「值 -> 字段名」的完整映射。
  U4. 字符串块里字段名与记录 id 的编号关系。已知 id 集合与字段名集合几乎等大，
      但**顺序不一致**，且存在 470 亿级的 id（如 458773=0x70015）说明 id 不是简单序号。
      未建立 id <-> 名字 的双射。
  U5. 每个字符串后面那个 32 位 key（1119 个不同值）。与 .mtl/.mdl 的 strtab 同构，
      在 jbcf/parser.rs 里也被标注为 "function is unidentified"。本任务未破解。
  U6. 那串 "…:(…):4" 尾部的类型码（观测到 1/2/3/4）的语义未确定；
