# P3-B-2 孤图理解 —— 证据可得性普查报告

**日期**：2026-09-22
**性质**：只读普查。未改任何库、任何游戏文件。
**目的**：在设计"孤图证据墙"之前，先核实计划里提的 6 类证据**到底存在不存在**。

---

## 结论速览

| 计划中的证据 | 实测可用率 | 判定 |
|---|---|---|
| 图片（像素） | 19,228 / 19,228 = **100%** | ✅ 已有 |
| 所在 pak | 19,228 / 19,228 = **100%** | ✅ 已有 |
| 尺寸（真实解码） | 19,228 / 19,228 = **100%** | ✅ 已有 |
| 格式（真实解码 codec） | 19,228 / 19,228 = **100%** | ✅ 已有 |
| **引用它的 mtl** | **0 / 19,228** | ❌ **不存在** |
| **附近资源** | **0 / 19,228** | ❌ **不存在** |

**四类真实存在且已在 `wall_v1.db` 里；两类是真的空。**

但普查过程中挖出了**两个比原计划更有价值的发现**（见 §4、§5）：

1. **贴图断链是"类型性"的，不是"孤儿性"的** —— 有伴图（5,032 张）同样 0 引用。
2. **`dangling` 里有 8,672 个真实存在的贴图名字**，带完整语义（角色/性别/部位/系统），
   这是"客户端本来想叫什么"的**直接证据**，是比"硬凑引用"好得多的抓手。
3. **孤图里有 6,669 张（34.7%）是"alpha 全零但 RGB 有内容"的图** —— 一个此前没被识别的独立类别。

---

## 1. 为什么"引用它的 mtl"是 0

### 1.1 孤图在引用系统里双向皆空

```
refs.to_hash 指向孤图（谁引用了它） ......  0 / 19,228
refs.from_hash 是孤图（它引用了谁） ......  0 / 19,228
relations 任一端是孤图 ...................  0
amembers（资产分组）里有孤图 .............  0 / 19,228
```

**关键对照**：有伴图（5,032 张）同样 `0 / 5,032`。
⇒ **这不是"孤图"的问题，是整个 `texture` 类型的属性。**

### 1.2 全库 61,408 条可解析引用里，指向贴图的只有 25 条

| 被指向的 type | 条数 |
|---|---|
| JBCF | 41,513 |
| ani | 11,294 |
| mesh | 8,549 |
| **texture** | **25** |
| set | 20 |
| JBPU | 7 |

引用系统本身是**通的**（JBCF/ani/mesh 都正常指过去了），**唯独贴图这一类没人指**。

### 1.3 那 25 条是"断掉的最后一跳"（重要线索）

25 条全部形如：
```
data/source/player/w1351_{nan,nv}/w1351_*_yifu/*.mtl
        ──> w1351_*_s_*.tga
```
解析命中的却是：
```
ui/icon/wardrobe/<同名>.tga
```
`.mtl` 想要的是 **3D 模型贴图**（无名的那张），结果只有**同名的 UI 衣柜缩略图**能被解析到。
**这证明数据里的命名链路是完整的，断在"解析那一步指错了对象"。**

---

## 2. 根因：客户端有**两套命名机制**，只覆盖了 UI 那一半

### 2.1 名字 → 实体 命中率，按扩展名分（差距悬殊）

| 扩展名 | 引用中的名字数 | 命中实体 | 命中率 |
|---|---|---|---|
| `.ske` | 1,872 | 1,628 | **87%** |
| `.mesh` | 4,780 | 3,697 | **77%** |
| `.mtl` | 5,590 | 4,078 | **73%** |
| `.ani` | 15,501 | 11,173 | **72%** |
| **`.tga`** | **8,696** | **25** | **0.3%** ⚠️ |

⇒ 排除"引用系统坏了"的可能。**是贴图这一类资源的"名字↔hash 映射"根本不在库里。**

### 2.2 两张名单完全不重叠

**有名字的贴图**：2,259 张，**100% 在 `ui/` 下**。名字前缀：
```
i_    (UI 图标)     875
icon_ (UI 图标)     825
f_    (UI 字体/图)  477
其他                 82
```

**被引用的 `.tga` 名字**：8,699 个，前缀分布：
```
<模型/场景贴图，无 UI 前缀>  8,699  (100%)
```

而 `refs` 里 `.tga` 引用的 `from_path` 以 `ui/` 开头的：**0 / 30,585**。

**两个集合交集为空。** 证据链：
```
ui/ 贴图      → 有名字（来自 ui 命名表）→ 但不被任何东西引用
模型/场景贴图  → 被 .mtl 大量引用       → 但没有名字
```

---

## 3. "附近资源"同样不存在

- **同目录**：孤图 `path` 全空（0/19,228），**没有目录概念**。
- **同 pak ±64KB 邻居**：抽查 5 张孤图，邻居确实存在（`geom`/`texture`/`JBCF`/`mesh`/`mapref`），
  但 PAK 是**顺序打包**，邻居只是"物理上碰巧写在一起"，**不是语义相关**。

> ⚠️ 硬用会**制造假关系**，直接违反项目第一原则（"没解出像素就不显示图/不制造假关系"）。
> **建议不做。**

---

## 4. ★ 发现一：贴图断链是"类型性"的

这是普查里最有分量的一条，也是**计划前提需要修正的直接原因**：

- 孤图 0 引用、有伴图 **也** 0 引用
- `.mtl` 引用 `.tga` 有 30,585 次，全部落到"名字对不上"
- 贴图有名字的 100% 在 `ui/`，被引用的 0% 在 `ui/`

**结论**：不是"孤图缺少上下文"，而是**整个模型贴图类在命名系统里就是"黑户"**。
所以"给孤图补引用证据"这件事，**对 19,228 张和 5,032 张一样，都做不到** —— 它不该按"孤图/有伴"来分，而该按"贴图 vs 其它类型"来分。

---

## 5. ★ 发现二：`dangling` —— 8,672 个真实存在的贴图名字

名字存在，就是没有主人。`dangling` 表共 14,377 条：

| ext | cls | 名字数 | 引用次数 |
|---|---|---|---|
| `.tga` | shared | 2,392 | **24,280** |
| `.tga` | unique | 6,280 | 6,280 |
| `.ani` | unique | 4,328 | 4,328 |
| `.mesh` | unique | 526 | 526 |
| `.mtl` | shared | 128 | 513 |
| `.ske` | shared | 232 | 464 |

**`.tga` 类：8,672 个名字、30,560 次引用，全部"对不上"。**

### 5.1 这些名字带完整语义（这才是真资产）

`refs` 里 `.tga` 名字的**引用者路径**，倒数第二段（部位/系统）分布：

```

    model          439                   npc/quest       3062
    ribbon_trail   278                   npc/changjingdaoju 237
    texture        269                   npc/model        214
    ring           180                   player/w1351_nan 206
    mask           161                   player/w1351_nv  191
    point_light    112                   npc/wuqi         176
    pattern        107                   npc/toukui       123
    plant          103
    smoke           93
    fire            62
    water           54
    ice             46
    lightning       42
```

**"角色_性别"段**：`w1351_nan` 224、（女）`w1351_nv` 198。

**名字后缀编号**（推测语义，需人工确认）：
```
_<无>  11816    _h  6005    _c  3674    _x  2197    _z 1506
_lf    1505     _s  1189    _l  1109    _b   857    _w  535
```

### 5.2 名字样本（一眼能读出归属）

```

w1351_nv_yifu     (133 个): w1351__mask_cx03.tga | w1351_mask_jiasha_h001.tga | ...

```

**人工判读可行性已验证**：这些名字**直接说明了它属于哪个角色、哪个部位、哪个特效系统**。

### 5.3 唯一的断点

```
名字  ✓ 真实（8,672 个 .tga 名字，带完整语义）
hash  ✓ 真实（19,228 张孤图，像素已解码）
      ✗ 中间那一跳（名字 → hash）不存在
```

对照 `.ani` 为什么能连上：
```
refs:  w1351_pets_lianyishou_b5_idle01.ani <- .../w1351_pets_lianyishou_b5.ske
解析:  resources.name = 'w1351_pets_lianyishou_b5_idle01.ani'
       resources.path = 'data/source/npc/quest/w1351_pets_lianyishou_b5/ani/...ani'
       → 名字能按 path 规则还原 ⇒ 对得上
```
`.tga` 缺的就是这一步：**贴图的 path 从来没被写进命名表。**

## 6. ★ 发现三：6,669 张孤图是"alpha 全零但 RGB 有内容"

按 alpha 覆盖率分层，19,228 张孤图：

| 类别 | 张数 | 占比 |
|---|---|---|
| **A 近全透明**（alpha_cov < 0.02） | **6,669** | **34.7%** |
| B 近似纯色（lum_sd < 3） | 85 | 0.4% |
| C 近乎平坦（edge < 2） | 913 | 4.7% |
| D 有内容 | 11,561 | 60.1% |

### 6.1 逐像素核对（读回真实 PNG）

```
0000b0286d98085c  64x64  alpha: min=0 max=0  非零像素 0/4096
                         RGB(全部像素) R=0.0 G=250.7 B=4.3
0007acc966654c3f  64x64  alpha: min=0 max=0  非零像素 0/4096
                         RGB(全部像素) R=0.0 G=188.1 B=66.9
000ea98eb383b6c6  64x64  alpha: min=0 max=0  非零像素 0/4096
                         RGB(全部像素) R=0.9 G=125.4 B=128.5
0019a18ddfc3e972  64x64  alpha: min=0 max=255 非零像素 118/4096 (2.88%)
```

**alpha 通道确实是 0，但 RGB 通道有真实内容**（各自不同！G=250.7 / G=188.1 / G=125.4）。
与 `wall_tex`、`raw.tsv` 三处数据一致（`mean_a=0.000`、`alpha_cov=0.00000`）。

### 6.2 这意味着什么

这**不是"空图"**——RGB 里有可区分的内容，dHash 也因此能把它们分到不同族。
它们更像：
- **纯遮罩图 / 蒙版**（RGB 存数据，alpha 留空）
- 或**渲染时需要外部赋 alpha 的通道图**

**这是一个此前没被识别的独立类别，应当单列，而不是混在"孤图"里。**

## 7. 孤图侧的结构（自证属性，100% 可用）

### 7.1 尺寸 × 真实 codec

| 尺寸 | codec | 张数 |
|---|---|---|
| **64×64** | **RGBA32** | **10,289** |
| 256×256 | BC3 | 3,002 |
| 1024×1024 | BC3 | 1,891 |
| 128×128 | BC3 | 941 |

**64×64 占 10,804 张（56%），其中 10,289 张是未压缩 RGBA32** —— 与"alpha 全零"那一类高度重合。

data2  6,032    data4  5,195    data1  3,080
data3  2,966    data    1,817    data_1   138

⇒ **不是集中存放的连续块**，而是**散落全库**。这条否掉了"整批来自某个被废弃的资源包"的猜想。

## 8. 对 P3-B-2 的建议：调整方向

### 8.1 做不到的（建议明确放弃）

- ❌ **"引用它的 mtl"** —— 孤图零入边，**对 19,228 张和 5,032 张一样做不到**。
- ❌ **"附近资源"（pak 邻居）** —— 物理相邻 ≠ 语义相关，硬用会造假关系。
- ❌ 为了凑证据去按名字模糊匹配 —— 名字↔hash 那一跳是断的，模糊匹配 = 编造。

### 8.2 能做的（都有真实数据支撑）

**A. 自证属性分层墙 —— 100% 可用，数据已在 `wall_v1.db`**
尺寸 / 真实 codec / mips / alpha 覆盖 / 亮度标准差 / 边缘能量 / pak。
**尤其新增"alpha 全零"这一层**（6,669 张），把"空通道图"和"真·有内容图"分开。

**B. 「名字户口本」—— 8,672 个无主贴图名字清单（推荐主交付物）**
把 `dangling` 的 `.tga` 名字，按**引用者路径**归类成可判读的清单：
- 角色维：`w1351_nan` / `w1351_nv` / `npc/quest` / `npc/wuqi` / `npc/toukui`
- 系统维：`data/effect/textures/{fire,ice,water,lightning,smoke,mask,ring,plant,...}`
- 每项带：引用它的 `.mtl`/`.mesh` 路径、引用次数、是否在 `ui/` 有同名孪生

**价值**：这是"客户端本来想叫什么"的**直接证据**，比看 19,228 张无字图高效得多。

**C. 「贴图命名缺口地图」**
把"贴图 vs 其它类型"的命名覆盖率做成一张对照图（87%/77%/73%/72% vs **0.3%**），
以及 25 条"断掉的最后一跳"的完整链路。这是**根因级**的发现，值得单独成文。

### 8.3 需要用户决策的

1. **64×64 alpha 全零那 6,669 张**，算不算"待理解贴图"？建议单列"空通道"类，不混进孤图口径。
2. **要不要做「名字户口本」**（B）？这是当前唯一能让"无名 ↔ 有名"产生真实交集的路线。
3. **要不要走"从名字反推 hash"**？—— 属于逆向战线，成本高、不保证收敛，建议**先不做**。

---

## 9. 一句话总结

> **孤儿贴图不是"数据缺了"，是"客户端压根没给模型贴图起名字"。**
>
> `.ani/.mesh/.ske/.mtl` 有名字（72–87% 能对上）；`.tga` 没有（**0.3%**）。
> 名字存在的地方是 `dangling`（**8,672 个 `.tga` 名字**），带完整语义，
> 但它和 19,228 张孤图的 hash 之间**没有桥**。
>
> 所以 P3-B-2 的正确形态是：
> **用已有的自证属性做分层（含新发现的"alpha 全零"类），
> 用 `dangling` 里的真实名字清单做人工判读的抓手，
> 而不是假装能给每张图挂一个"引用了它的 mtl"。**

## 附：可复现的查询口径

```sql
-- 孤图集合
select t.hash from wall_tex t join wall_family f on f.fid=t.fam where f.n=1;

-- 孤图入边（结果 0）
select count(distinct to_hash) from refs where to_hash in (<孤图hash>);

-- 名字→实体 命中率（核心证据）
select substr(rf.name, instr(rf.name,'.')) e,
       count(distinct rf.name) dn, count(distinct res.hash) dh
from refs rf left join resources res on res.name = rf.name
group by 1 order by dn desc;

-- 有名字贴图的目录（2259/2259 全在 ui/）
select sum(case when path like 'ui/%' then 1 else 0 end), count(*)
from resources where type='texture' and name is not null and name<>'';

-- alpha 分层
select case when alpha_cov<0.02 then 'A 近全透明'
            when lum_sd<3 then 'B 近似纯色'
            when edge<2 then 'C 近乎平坦'
            else 'D 有内容' end k, count(*)
from wall_tex t join wall_family f on f.fid=t.fam where f.n=1 group by 1;
```

## 附二：本次普查自身的两个坑（均已修正）

1. **列错位**：`_p3b2_deep64.py` 里 `select count(*), min(lum_sd), ...` 输出时少读一列，
   导致打印出 `lum_sd [0.0 .. 35.35] avg=60.01` 这种 **avg > max 的物理不可能值**。
   —— 正是项目里已经用测试守住的那一类 bug，**靠"avg > max"这个荒谬数值才被发现**。
2. **不要用 anti-join 查 3 万行 × 4.5 万行**：`refs` left join `resources` on name 会超时被 SIGTERM。
   改成先把 `resources.name` 读进 Python set、再逐行过滤，秒级完成。
