# cfg 身份普查：4,780 个匿名条目拿到真路径，但**不能**喂给动画线（2026-10-11）

工具：`cargo run --bin cfg_named`（`crates/core/src/bin/cfg_named.rs`，只读；给 `--out=` 才落盘）。
原理一句话：引擎的 pak 索引哈希就是 `path_hash(原始全路径)`，把 `ResourcePath.cfg` 的
72,764 条「裸名→全路径」逐条代进去，就能问出「这个匿名包内条目到底有没有路径身份」。

## 复现与新增的数（2026-09-26 那三个总数分毫不差）

| 项 | 数 |
| --- | --- |
| cfg 映射对 | 72,764 |
| 清单里已有路径的行命中 | 42,083 |
| 包里没这件（源被剥离） | 25,900 |
| **命中但清单没记路径（白捡身份）** | **4,780** |
| 同一哈希被两条不同 cfg 路径命中 | **0**（哈希唯一性再钉一次） |

白捡那 4,780 条按扩展名：`ani 2,995 · mesh 468 · mtl 324 · walkplane 296 · mdl 232 · ske 232 ·
pu 223 · scene 6 · terraininfo 4`。**贴图 0 条。**

旁证（不依赖 cfg 的扩展名，只看库里按内容判的 type/subtype）：`.ani`→`ani/copy`、`.mesh`→`mesh`、
`.mtl/.mdl/.ske`→`JBCF`、`.pu`→`JBPU`、`.terraininfo`→`mapref/tab280`、`.scene`→`tiny`/`set`——
逐类都对得上，没有一类串到别的内容格式上。所以**这 4,780 个身份是硬的**。

## 但「主力是动画」≠「动画线有增量」——我上一轮那句要说错了

`709bae6` 的提交信息里我写「这批的绝对主力是动画（62.7%）」，紧接着在对话里补了一句
「2,995 个 .ani 现在有确定身份了，下一步可以接的活不用等你」。**后半句撤回**，实测是这样：

- 拿 sidecar 的目录去和组表 `agroups.dir` 对：**先按全等**，`.ani` 2,995 条**全部不匹配**；
  改成**祖先目录匹配**（`.ani` 落在 `…/<角色>/ani/`，而组目录只写到 `<角色>`）也只有
  **2 条**归得进现有组，2,993 条归不进。
- 为什么归不进：抽三个角色查——`w1351_pets_daishu_b1_2_3`、`w1351_pets_jiuxiaozhanlong_b8`、
  `w1351_pets_yazuishou_b1`——**清单里带路径的行数都是 0，组表里也没有同名的组**。
  当时据此写的「这些角色的网格/材质整批被剥掉了，动画是**孤儿件**」**说粗了**：
  下面「已结案」那一节量准了——它们是**进阶形态**（`_b1…_b8`），224/235 的 `_b0` 本体在清单里资产齐全，
  变体自己的 `.mesh/.mtl/.ske/.tga` 是被引用着的、只是包里没放。
- 规模：这 2,995 条匿名 `.ani` 分布在 **235 个角色目录**，其中角色名能在组表 `stem` 里找到的只有
  **3 / 235**。条数最多的：`w1351_boss_machao` 15 条、`w1351_pets_huaxianzi_b1…b8` 各 14 条。

**所以正确结论是**：这次普查没有给动画播放/导出增加任何可用的新内容（能挂到现有模型上的只有 2 条），
它给的是**目录线的一笔新账**——「235 个角色只有动画在包里」是一类此前没单独数过的缺口
（与 `catalog-baseline-undercount` 那 1,799 条不同源：那批是组数少，这批是角色整组资产被剥离、
只剩下动画件）。

## 写这句话之前做过的对抗自查

「只剩动画」听起来像推论，所以专门去否它自己：把 4,780 条按角色目录归堆（`.ani`/`texture` 这类
角色子目录那一层剥掉），只看含匿名 `.ani` 的那 235 个目录，问它们**还装不装别的件**——
若装了，就说明这些角色是完整组、只是清单没名字，那「孤儿」这个说法就得撤回。
实测：**同时有 `.mesh` 且 `.ske` 的 0 个、有 `.mesh` 的 0 个、有 `.mdl` 的 0 个，
235 个目录全部只有 `.ani` 一种扩展名**。另一种解释（完整组没命名）被否掉，说法保留。

## 再往下一层：变体的动画与本体 `_b0` 是**同一套动作名**（2026-10-11 夜）

「能归进现有组的只有 2/2,995」是按**目录归组**算的，那句容易被读成「这批动画没用」。
换个问题量：变体形态（`_b1…_b8`）那 13 条动画的动作名，和清单里本体 `_b0` 的动作名是不是同一套？
做法：把每条 `.ani` 的文件名剥掉角色前缀得到动作名（`X_fight_idle01.ani` → `fight_idle01`），
再与同族 `_b0`（清单里有路径的那些）的动作名集合比：

| 项 | 数 |
| --- | --- |
| 能拿到同族 `_b0` 动作集的变体目录 | **226 / 235** |
| 变体动作集是本体动作集的**子集**（含相等） | **225** |
| 恰好**完全相等** | **221** |
| 与本体**一个都不重合** | **0** |
| 变体里出现过的动作名共 21 种，其中从没在任何 `_b0` 出现过的 | **4** |

高频动作名两边同一批：`idle01/idle02/idle03/run/walk/dead/hit01/hit02/skill01…`。

**这句能说到哪儿、不能说到哪儿**（说到这儿为止都还是文件名层面的统计）：

- ✅ 能说：变体形态用的**动作词汇表**与本体一致，不是自造一套。
- ❌ **不能说：这批动画能直接拿本体的骨架播。** 那要证的是**骨架同一套**，
  证据只能是 `.ani` 的轨道骨名 vs `_b0` 的 `.ske` 骨名（两边都已能解，见
  [[ani-animation-format]]：轨道骨名是父骨链的独立旁证，2,307/2,318 全对）。
  **这一步本档案还没做**，是下一枪，也是判断「动画线到底有没有 +2,995」的唯一判据。
- 下一枪的具体做法：挑 3 个族（宠物 `_b0`/`_b3`/`_b8`），从 pak 里各取一份变体 `.ani`
  与本体 `.ske`，比轨道骨名集合的交集比例；同族骨名若一致，才谈得上把变体动画挂到本体模型上。

上面「304/304 全在」与随后 bone_order 跑出的「280 条有本体没的骨名」**互相矛盾**，
而我一核 schema 就发现两遍都在拿不严谨的字段做集合比较，所以**两个数一起撤回**，
留下的只有这条方法论：

- 变体文件（`--ani` 导的）里 `nodes` 与 `parentChain` **都是 0 条**（它是动作，不是骨架），
  轨道名在 `animations[].tracks[].bone`，另有 `animations[].bones` 是**另一份表**——
  我那两版采集器把 `animations` 整段按键名 `bone|name|child|parent` 递归抓，
  等于把两份表混成了一个集合。
- 本体文件里 `parentChain[0]` 是 `{"name": "000", "parent": null}`——这是没解出父链时的填充名，
  不是骨名；而我的 `keys_of()` 把 parentChain 整段也抓了进来。
- `nodes[]` 的骨名键我**没核过**（对象很长，第一眼只看到 `bind`/`bindPosition`），
  所以 bone_order 那一版拿 `nodes[].bone|name` 取到的到底是几个真骨名，我自己都说不清。

**正确的做法（下一枪照这个做，别再手写递归抓键名）**：
让 `skel_dump` 明确输出两个有序数组——`boneOrder`（骨架节点顺序，取 `nodes[].` 里那个真名键）
与每条动画的 `trackOrder`（`animations[].tracks[].bone`，按出现顺序），
比较只在这两个数组之间做。这样顺序与集合是一回事、也不会把 `bones`/`parentChain` 混进来。

已经确认没跑的结论只剩一条：**变体 `.ani` 能用 hash 定位并解出轨道**（`--ani 0038b6df39665372`
= `w1351_pets_yazuishou_b1_vertigo.ani`，33 骨 · 24 帧，工具链通）。
「变体动画能不能拿本体 `_b0` 的骨架播」回到**未测**，不是「已支持」也不是「不支持」。

顺带一条不该被忽略的旁证：轨道骨名是 `bip01`、`bip01_head` 这一族，
而 exe 里 `bip01` 出现 **0 次**（README 已推翻清单里那条）——所以这些名字来自数据文件本身，
不是引擎内置模板。这一条与本轮结论无关，但下一枪比顺序时会用到同一个数据面。## 比较对象选错了才是这两轮打架的原因（2026-10-11 深夜，schema 核完）

把字段读到底之后，问题不在空值、也不在混抓键名，而在**拿一份网格的骨架去比一副骨架**：

- `nodes[].name` 才是骨名键；本体 `w1351_pets_yazuishou_b0` 那一轮只导出了**一份**网格，
  解出的骨架节点 **23 根**（`bip01`、`bip01_pelvis`、`bone02`、`bip01_spine1`、`bip01_l_calf`…）。
- 而变体 `.ani` 的轨道骨名有 **61~83 根**（例：`w1351_boss_machao_*.ani` 83、`…_bawanglong_b2_*` 61）。
- `animations[].bones` 是一个**整数计数**，不是名单——上一版脚本把它当列表递归抓，等于又造了一个假集合。

这正是 10-10 已经记过的现象：**网格只声明自己那部分骨**，一副骨架要靠**同目录全部件网格的并集**
（`zhaotianshi`：部件链 118 根 + 动作另 59 根 = 177，与「主网格 ∪ 四份部件」逐数对上）。
所以「23 根里装不下 61 个轨道名」不是变体动画对不上本体，而是**我对本体只取了一份部件网格**。

**下一枪照这个做，才算把这一层钉死**：
1. `skel_dump` 对本体导**该组全部网格**的 `nodes[].name`，取并集（现有 `--name` 只挑最大的一份，要加 `--all-meshes` 或直接按目录遍历）；
2. 顺序比较用两个有序数组：骨架并集的名字集合、动画轨道的**去重名单**；
3. 顺带把「轨道比并集多出来的骨名」报出来——那些是动画专用骨（`footsteps` 一类），
   播放管线按骨名重挂，多余的骨名不该判成错。
在这一版做完之前，「变体动画能不能拿本体骨架播」仍然是**未测**，两轮的数都别引用。
## 并集版跑坏了：是我脚本的路径切分 bug，不是结论（2026-10-11 深夜）

`.scratch/dyn/union_compare.py` 这一版思路对（本体取同目录**全部件网格**的 `nodes[].name` 并集，
再与动画轨道去重名单比），但跑出来每族都是「网格 1 份 · 并集 **0** 根」，
逐行打印里那份网格的名字是**空串**（`各份网格自报骨名： :0`）——
我从 `resources.path` 取文件名那一步把 basename 切成了空，于是并集永远是空集，
「12 条全都不在并集里」这句话**只描述了我的 bug**。

所以「变体动画能不能拿本体骨架播」**仍是未测**，别引用今天任何一版数字。
可以确认的只有工具侧两条：匿名 `.ani` 能按 hash 定位并解出轨道（33 骨 · 24 帧那条），
动画轨道的骨名与骨架节点同属 `bip01_*` / `boneNNN` 这一族命名。

修的地方很小：取文件名要用 `os.path.basename` 或按 `max(path.sep, '/')` 之后再切，
别对切出来的名字直接砍掉 5 个字符；并在并集为 0 时**停下来报错**，
而不是继续把「0 根」当成骨架去比——一个空集合会把所有比较都判成「对不上」，
这正是今天第三次造出假阴性的同一形状。**比较之前先断言两边都不是空集**。
