# 父骨链线索：.mesh 尾部「只有名字的骨」其实是子骨名单（2026-09-30 实测）

## 为什么值得单开一份

v0.5.0 播放卡在两处：父骨链、蒙皮权重。父骨链此前证伪过七条去处
（见 `.scratch/动画骨架_线索_20260929.md`），今天在同一份文件里看到了**第八个候选，
而且这一次是内容对得上的**：`bip01_spine` 那条记录后面，紧跟着一串
`bip01_spine1 / bip01_l_thigh / bip01_r_thigh / bone10 / …`——
这正是一根标准 Biped 脊柱该有的子骨。文件头声明 46 根骨、节点表只认出 36 根，
差的那 10 根（`bip01_footsteps / bip01_spine1 / bip01_neck / bip01_head /
bip01_l_clavicle / bip01_l_thigh / bip01_r_thigh / bip01_l_finger0 / bip01_l_finger1 / …`）
全部出现在这份名单里——它们不是「没有矩阵的坏数据」，而是**以名字形式挂在别的骨后面**。

## 用的样本与工具

- 文件：`.scratch/ani/w1351_monster_xiyuqiezei_yifu_001.mesh`（52,536 字节，
  `0x110` 处声明 46 根骨，`parse_nodes` 认出 36 条带矩阵记录）。
- 复刻 `crates/core/src/preview/geometry.rs:read_node` 的判定，按 4 字节步长扫全文件，
  把「带矩阵的记录」与「只有名字的位置」按文件顺序排出来：脚本 `.scratch/node_scan.py`，
  结果 `.scratch/mesh_nodes_ordered.json`（36 条记录 + 112 个只有名字的位置）。

## 看到的排布（偏移都是实测）

```
* 0x007798 bip01                          ← 96B 记录（名字 + 绑定矩阵）
  0x007858 bip01     0x007878 bip01       ← 自己的名字，两遍，32B 一条
  0x00789c bip01_footsteps                ← 然后是一串子骨名
* 0x0078bc bip01_pelvis
  0x00797c bip01_footsteps 0x00799c bip01_footsteps
  0x007a60 bip01_pelvis    0x007a80 bip01_pelvis
* 0x007aa4 bip01_spine
  0x007d9c bip01_spine     0x007dbc bip01_spine
  0x007de0 bip01_spine1    0x007e00 bip01_l_thigh   0x007e20 bip01_r_thigh
  0x007e40 bone10          0x007e60 bone10_mirror02 0x007e80 bone10_mirror01
* 0x007ea0 bone10_mirror02_mirror01
```

36 条记录里 23 条的名单以「自己两遍 + 子骨若干」开头；另外 13 条对不上，
对不上的那些名单里出现的都是**别的骨的名字两遍**（例：`bone09` 那条后面是
`bip01_l_finger0×2, bip01_l_finger1×2, bone09×2, bone08×2, bip01_r_clavicle×2`）。
所以「×2」不是子骨标记，更像是**每根骨在名单里出现两次的一次登记**——
同一段名单被我用「记录在前」还是「记录在后」两种归属切了一刀，两种切法各能对上大半。

## 还没吃下来的那一块

记录与记录之间的间隔不是 96 也不是 32 的整数倍：
`0x78bc-0x7798=292`、`0x7aa4-0x78bc=488`、`0x7ea0-0x7aa4=1020`、`0x8214-0x7ea0=884`。

**间隔里有什么，今天看到了**——每条 96B 记录之后紧跟一段
`[u32 头][u32 0][u32 索引 ×N]`（实测原字节）：

```
记录@0x7aa4 bip01_spine    之后：47 00000000 | 01 02 03 06 0b 0c 0d 10 1a 31 32 33 34 35
记录@0x7ea0 bone10_mirror02_mirror01 之后：4a 00000000 | 01 02 03 04 05 06 …
记录@0x8214 bone05         之后：7f 00000000 | 04 05 07 08 09 0a 0e …
记录@0x7798 bip01 / @0x78bc bip01_pelvis 之后：全 0 + 0x3f7ff605（是浮点，不是索引表）
```

三点要记着：
1. 索引一律**严格递增**，值域 1~53（这份文件 46 根骨、子网格数未知），
   所以它像「这根骨影响哪些子网格/面片」的清单，**不像父骨索引**
   （父索引不会天然有序，也不会从 1 开始连排）。
2. `origin`、`top`、`bip01`、`bip01_pelvis` 这些根骨后面没有索引表，是浮点填充
   （`0x3f7ff605` ≈ 1.9999）——同一偏移在不同骨上含义不同，说明这一段的长度是变长的，
   头那个 u32（0x47=71、0x4a=74、0x7f=127）很可能就是**这一段自己的字节数或元素数**。
   先把这个长度对上，才谈得上读后面的东西。
3. 因此父骨索引更可能在「名字名单」与「这段索引表」之外的第三处。

IDA 那边给了一个数量级吻合的提示：`EsSkeleton` 对象 +192 处指向一个数组，
元素是 **18 个 qword = 144 字节**一条（`.scratch/ida_vt_out.txt`、
`.scratch/ida_ctor.txt` 里 `sub_14073FA60` 的 `v12[18 * *(v12-1)]` 那一段）。
文件里每根骨大概率就是「96B 名字+矩阵 / 变长索引表 / 32B 名字×N」三件套，
父骨索引藏在其中还没对上长度的那一段里。


## 下一步（按这个顺序做，别再从名字猜）

1. 先把那条变长索引表的**长度字段对上**：头 u32 与后面元素个数、与到下一条记录的距离
   三者关系定下来（脚本：`.scratch/node_scan.py` 已能按文件顺序列出记录与名字槽）。
2. 用两份骨数不同的 .mesh（46 根与 20 根左右）对同一位置做差分：
   父骨索引应该随骨号变化，且值域在 [0, 骨数) 内；今天看到的索引表值域到 53 > 46，
   所以它多半不是父骨——差分可以一次确认这一点。
3. 交叉验法（不靠读格式也能判对错）：解出来的父骨必须让
   `|child.bind - parent.bind|` 落在合理的骨长区间（0.01~2.0），且整棵树单根、无环。
   这一条能一次否掉错的偏移选择。
4. 若 1~3 落空，回到 IDA：`sub_14073F7A0`（另一处写 `EsSkeleton::vftable` 的地方，
   0x246 字节）才是构造本体，顺着它的调用者找 .mesh 解析函数，看它往那 144B 里填了什么。
   IDA 通道脚本：`.scratch/ida_rpc.py`（裸 JSON-RPC，13337 端口）、
   `.scratch/ida_call.py`（按文件传参调工具）、`.scratch/ida_de.py`（批量反编译）。
   虚表与对象布局的导出在 `.scratch/ida_vt_out.txt`。

## 顺带钉掉的两个事实

- `parse_nodes` 认不出那 10 根不是 bug：它们在这份文件里确实没有 96B 记录。
  界面文案「文件头声明 46 根骨，这里认出 36 根」是对的，但原因要说成
  「另外 10 根以名字形式挂在别的骨后面」，不能再说成「名字后面不跟矩阵，不知道为什么」。
- 蒙皮权重仍然不在 `.mesh` 里（此前多轮实测），父骨链即便解开，模型本身还是不会跟着变形。

## 已算过的一条：拿 bind = local ∘ bind_父 反解（2026-09-30 晚，**不成立**）

权重解出来之后多了一个抓手：绑定位移是世界系（左右镜像对验过），`.ani` 每骨每帧是局部位姿，
那 `bind_i ≈ local_i ∘ bind_父` 该成立，残差最小的那个 j 就是父。脚本 `.scratch/parent_from_bind.py`，
跑在 `w1351_monster_xiyuqiezei_yifu_001` 上（节点 36、轨道 45、两边都有名字的 30）：

- 四种口径组合（四元数换序 × 行向量乘序两种）最好的一组只有 **1/30** 根残差 < 0.05，
  而那 1 根是 `bip01 → origin`（残差 0.000，本来就是单位阵附近，等于没信息）。
- 其余残差 0.77~1.55，量级就是「不相等」。
- **判据本身错了**：`.ani` 的第 0 帧是走路动作的第一个姿势，不是绑定态；
  拿它当 rest 去对 bind，等式天然不成立。要用这条得先拿到 rest 位姿
  （`.ani` 骨架区 +12 那个单位四元数才是候选，但 `+48` 已被证伪不是绑定位移）。
- 副产品：残差最小的候选父**有一半解剖学上是对的**（`bone12→bone11` 四份镜像全对、
  `bip01_l_toe0→bip01_l_foot` 标准 Biped），也有明显错的（`r_toe0→l_toe0`、`r_calf→r_hand`）。
  这条不能当结论用，但说明「残差排序」里混着真信号——换成 rest 位姿后值得再跑一次。

## 权重解出之后连带改掉的假话

`skel_dump` 导出的 JSON 里原先写着 `missing.skinWeights = 蒙皮权重未解`，现在权重已解，
这句话是假的：改成把每骨的 `[顶点号, 权重]` 放进 `nodes[].influences`，
并把「带不带表按份算」（衣服 26 根、手套 0 根）写进 `missing.skinPerPart` 与 `provenance`。
闸门 `dump_carries_nodes_tracks_and_says_what_is_missing` 钉住：至少 20 个节点带 influences、
顶点号严格递增、`missing` 里不许再有 skinWeights。反向验红：把导出键名改成 `influencesX` → 红（报「导出里只有 0」）。
