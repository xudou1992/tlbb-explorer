# 冷启动性能：114.6s → 2.4s（一个索引搞定）

## 定位过程（不是猜，是量出来的）

### 1. 先看度量本身在哪
`app/src-tauri/src/data.rs` 里 `warm()` 打了两个计时：
`t_collect`（清单查询）和 `t_decode`（主体回读），都是**各分片累计**。

原报告：`总 114.6s（清单查询 1278.7s · 主体回读 5.3s）`
—— 注意 1278.7s 是 16 路分片的**累加**，除以 16 才是真实墙钟贡献（≈80s）。

### 2. 把 collect() 的四条查询逐条计时（200 组样本）
| 查询 | 200 组耗时 | 推全量 13,080 组 |
|---|---|---|
| `members()` | 143.1 ms | ≈0.86 s |
| `refs_from()` | 10.5 ms | ≈0.64 s |
| `group_names()` | 9.0 ms | ≈0.41 s |
| `tags()` | 5.6 ms | ≈0.40 s |
| **`textures_in_dir()`** | **51.8 ms** | **≈88 s** |

**五条里四条加起来 2.3s，第五条一个人 88s。** 这就是全部问题。

### 3. 看执行计划找到根因
```
-- 修复前
SEARCH resources USING INDEX ix_res_dir (dir=?)
USE TEMP B-TREE FOR ORDER BY          <-- 元凶
```
`textures_in_dir` 的语句是：
```sql
SELECT hash, path FROM resources
WHERE type='texture' AND dir = ?1
ORDER BY original DESC LIMIT 8
```
`resources` 上只有 `ix_res_dir(dir)`（单列）。SQLite 只能用 `dir` 定位，
然后**把整个目录的行全取出来**（回表读 type/original/hash/path），
**再在临时 B 树里排序**，最后取前 8。
而这条查询要跑 **12,159 次**（每个非空 dir 一次）。

### 4. A/B 对照（排除缓存效应）
同一份库复制两份，一份 `DROP INDEX`，交替各跑 3 轮 12,159 次调用：

| | 第1轮 | 第2轮 | 第3轮 |
|---|---|---|---|
| 无覆盖索引 | 52.72s | 83.42s | 98.59s |
| **有覆盖索引** | **0.74s** | **0.76s** | **0.74s** |

**约 110 倍**。而且对 6 个测试 dir 的返回结果**逐行完全相同** —— 只是变快，没改语义。

## 修复内容

### ① 数据库索引（主因）
```sql
CREATE INDEX ix_res_dir_type_original ON resources(dir, type, original DESC);
ANALYZE;
```
这是一条**覆盖索引**：`dir` 定位、`type` 在索引内过滤、`original DESC` 满足排序。
计划变成：
```
SEARCH resources USING INDEX ix_res_dir_type_original (dir=? AND type=?)
```
**临时 B 树消失**。库 141.9 → 145.5 MB（+3.6 MB，+2.5%）。

### ② 建库脚本 `dbbuild.py`
- 在 `build()` 的 `executescript` 里加建该索引（带原因注释）
- 新增 `analyze()`，在 `main()` 末尾调用 —— 保证每次重建库后统计都是新的

**为什么加 `ANALYZE`**：没有 `sqlite_stat1` 时规划器只能靠猜行数，
同一个查询在不同入口可能选中不同计划 —— 这正是 P3-C 之前
「工作台和报告对同一个资产说法不一致」的同一类根因。

### ③ Rust 侧 `Catalog::open_ro`
加了 `PRAGMA cache_size = -16384`（16 MiB/句柄）。
工作台每个分片开一个句柄（最多 16 个），默认页缓存远小于热工作集，
分片之间互相驱逐页面、反复重读同一批 B 树页。16 MiB × 16 ≈ 256 MiB，
比 145 MB 的库还大，等于整库常驻，不需要额外做缓存步骤。

### ④ 回归测试 `crates/core/tests/query_plan_audit.rs`（3 个）
这个故障是**静默的**：把索引删掉，什么都不报错，只是慢 50 倍。
所以断言写的是**执行计划**，不是计时（计时在任何机器和负载下都不稳定）。

- `textures_in_dir_is_answered_by_a_covering_index` —
  必须走 `ix_res_dir_type_original`，且**不得出现 `TEMP B-TREE`**
- `the_per_group_queries_all_stay_index_backed` —
  四条每组查询都必须按 gid/from_hash 走索引寻找，不得出现 `SCAN `
- `the_planner_has_real_statistics` — `sqlite_stat1` 必须存在

**反向验证过**：造一份去掉索引的库跑测试，确实变红，报错信息直接点名
「`textures_in_dir` 不再走覆盖索引，冷启动会退回 50 倍慢」。抓得住的测试才算数。

> 写测试时被工具纠正了两次，都是好事：
> 1. `group_names` 实际走的是主键自动索引 `(gid, name)` 而不是 `ix_an_g` ——
>    因为前者**顺带满足了 `ORDER BY name`**，是更优计划。按名字钉死反而是在钉一个更差的计划。
> 2. `EXPLAIN QUERY PLAN` 打印的是**别名**（`SEARCH m USING INDEX`）不是表名。

## 结果

| | 修复前 | 修复后 |
|---|---|---|
| 冷启动墙钟 | 114.6 s | **3.2 s** |
| `全部读取`（warm） | ~114 s | **2.4 s** |
| 清单查询（16路累计） | 1278.7 s | 34.6 s |
| 主体回读（16路累计） | 5.3 s | 15.5 s |
| 库体积 | 141.9 MB | 145.5 MB |

三次连测：3.20 / 3.20 / 3.23 s —— **稳定**，不是运气。
比用户定的「10 秒级」目标还快 3 倍。

**语义零变化**：`曹霜`→1、`宠物`→914、`boss`→841 命中数不变；
等级分布 `A0/B2601/C10479/D0` 不变；所有卡片仍然 `图：无`（没伪造预览）。

**测试**：132 passed / 0 failed（原 129 + 新增 3）。

## 顺带发现（不是本次修复范围，但值得记）
- `主体回读` 从 5.3s 涨到 15.5s 是**假象**：它和清单查询在同一个批次里串行，
  之前被 88s 的查询完全掩盖，现在暴露出来了。绝对值很小，不影响结论。
- `名称可定位 0/22605`、`带贴图线索 22` —— 与 P3-B-0 的结论一致：
  无名贴图没有名字可恢复，因此贴图引用只能停在「只有名称」。
  这不是性能问题，是数据事实。
