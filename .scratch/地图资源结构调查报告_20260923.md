# 地图资源结构调查报告

> 2026-09-23 只读勘察。目的：在写任何地图代码之前，先量清楚客户端里地图到底是什么形态。
> 数据来源：`resources.db` 只读查询（`file:...?mode=ro`）+ `view.exe` 字节导出。
> **未修改任何文件，未猜任何格式**；凡没验证过的都标"未知"。

---

## 一句话结论

地图数据不在 `data/` 下，而是两个顶层目录：**`mobile_maps/`（302 张地图的格子与索引）+ `mobile_maps_source/`（3,264 个物件网格）**。
物件这条链**已经通了**——`.scene` 记录里直接嵌网格文件名，抽样 4 个名字 4/100% 能在清单里定位到实体，而网格解析是阶段 1 已完成的能力。
地形 `.map` 与索引 `.sfl` 的**语义还没解出**，这是阶段 2 的真实工作量所在。

---

## 1. 地图入口在哪

| 位置 | 内容 | 数量 | 体积 |
|---|---|---|---|
| `mobile_maps/<地图ID>/` | 每张地图的分块与索引 | 302 个目录（其中 267 个已被 Catalog 聚成组） | 399.8MB |
| `mobile_maps_source/` | 地图物件的几何与材质 | 3,264 `.mesh` + 3,201 `.mtl` | 110.2MB + 4.1MB |
| `data/tani/` | 未知（扩展名 `.tani`） | 2,560 | 11.7MB |

单张地图目录里的文件类型：

| 扩展名 | 作用（实测依据） | 覆盖地图数 | 规模 |
|---|---|---|---|
| `.map` | 地形 | 220 / 302 | 最大 2.30MB（`w1351_fb_sxzc_001`），常见 1.7–1.8MB |
| `.scene` | 格子内的物件清单 | 300 / 302 | 共 11,933 个；平均每图 39.8 个，最多 133 |
| `.sfl` | 地图索引（**JBCF 容器**） | 297 / 302 | 600 – 11,184 字节，平均 5,916 |
| `.nav` | 导航/碰撞（本阶段明确不做） | 25 | 平均 5.4KB |

地图 ID 前缀分布（按 `.sfl` 数）：**fb 146（副本）、ll 105、gj 40、hd 2、cj 2、empt 2**。

> ⚠ **地图没有中文名**。全库 `agroup_names` 里含中文的登记名只有 10 条，`settings/` 下只有
> `GameWorldConstList.ini`、`GMCmd.tab`、敏感词表，**没有地图 ID → 中文名 的表**。
> 所以界面只能显示客户端原文 ID（如 `w1351_ll_dl_003`）。按红线 2，**不编中文名**——
> 想给用户"洛阳/苏州"这种叫法，只能靠人工标注回流，不能靠猜。

## 2. 地形是什么格式 —— 未知（有结构，无语义）

`.map` 开头 12 个 u32：

```
[1, 20, 21, 152, 1747352, 187, 1765304, 0, 0, 72362624, 460, 20776608]
```

已确认的事实：
- 第 7 个数 **1765304 恰好等于文件大小** → 说明头部有块表/偏移表
- 前 3KB **零可打印字符串** → 地形不嵌文件名，是纯二进制栅格
- `20 × 21 = 420`，形态上像地块栅格，但**没有任何证据支持这个解释，不下结论**

未解的问题（阶段 2 的主要工作量）：
1. 高度数据在哪、什么类型（u16 栅格？f32？压缩？）
2. 地块尺寸与坐标原点（`152`、`187` 是什么）
3. 地形贴图怎么指定（`.map` 里没名字，可能在 `.sfl` 或引擎侧）

**结论：第一版不要承诺"还原真实地形起伏"。** 见第 6 节。

---

## 3. 静态物件怎么放 —— 链已通，记录布局待定

`.scene` 文件名就是格子坐标：`<a>_<b>_<c>.scene`，**带负数**（如 `1_1_-3.scene`、`1_10_-1.scene`）。

头部实测（`w1351_fb_langhuanyudong_001/1_1_-3.scene`，20,937 字节）：

```
u32 28      —— 头部长度
u32 749     —— 条数
f32 1.0     —— 紧随其后的浮点常量（疑似缩放）
```

**记录里直接嵌网格文件名**，且名字前面是位置与缩放：

```
@0x003c  f32 59.6   f32 -3.74   f32 -59.8   f32 1.0
@0x004b  "w1351_cj_hehua_001.mesh"
```

在 4KB 采样内，相邻网格名的间距**恒为 757 字节**（5 次测量一致）→ 定长记录 + 名字尾。

| 观察 | 状态 |
|---|---|
| 记录含「位置 + 缩放 + 网格名」 | ✅ 已证实（字节可读，名字可解析） |
| 名字能否定位到实体 | ✅ 抽样 4 个，**4/4 命中 `mobile_maps_source`** |
| 空格子怎么表示 | ✅ 4 字节的 `tiny` 文件（11,933 个 `.scene` 里大量是这种） |
| 记录确切布局 | ❌ **未定**：头部声明 749 条，而 749 × 28 = 20,972 ≈ 文件 20,937，与实测 757 步长不自洽。两种解释都没验证过，不下结论 |
| 旋转怎么表示 | ❌ 未找到（采样里 1.0 只像缩放） |

## 4. 有没有索引 —— 有，而且是已会的格式

**`.sfl` 是 JBCF 容器**（magic `4a 42 43 46`，版本 8），每图一个，297 个。
阶段 1 已经有 JBCF 解析器（`.mtl`/`.mdl`/`.ske` 都靠它），所以**解码这一步不是从零开始**；
缺的是**语义**——`summary.rs` 目前把 `.sfl` 判成"未知"，没有专用预览器。

值得先查的问题：`.sfl` 是不是"格子坐标 → `.scene` 文件"的表？如果是，物件链就完全闭合了。

---

## 5. 贴图怎么组织 —— 和角色一样断链，且更彻底

对 `mobile_maps_source/` 下材质的引用实测：

| 引用类型 | 条数 | 能对上实体 |
|---|---|---|
| `.mtl`（父材质） | 3,288 | **3,288（100%）** |
| `.tga`（贴图） | 6,379 | **0** |

也就是说：地图物件和怪物/服装一样，**几何在、材质在、父材质在，只有贴图名落不到文件**——
这是客户端发布时不保存贴图路径的设计（与阶段 1 结论一致），不是解析失败。
地形贴图的组织方式（一张大图 vs 分块）**未知**，`.map` 里不含名字。

> 直接推论：**阶段 2 结束时地图仍然是灰模**。贴图恢复是阶段 3 的活，不要混进来。

## 6. 能不能先出灰模地图 —— 能，但要绕开未解的两块

建议的第一版目标（对齐"打开地图 → 看到物件位置 → 能旋转"）：

```
.sfl (JBCF，已有解码器)
   ↓  解出格子清单
.scene（每个格子）
   ↓  解出 (网格名, 位置, 缩放)   ← 记录布局需逆向，这是主要工作量
网格名 → hash → 阶段 1 的 mesh 解析
   ↓
GLB / WebGL 灰模 + 格子坐标地面
```

**第一版明确不做**：
- ❌ 真实地形起伏（`.map` 未解）——用**平地 + 格子网格线**代替，并写明"地形格式未解，这是平地替身"
- ❌ 贴图/颜色（阶段 3）
- ❌ 碰撞、寻路、`.nav`（不做）
- ❌ 中文地图名（没有表，不编）

**第一版验收**：
打开 `w1351_ll_dl_003` → 看到 N 个建筑/树木灰模摆在格子位置上 → 能旋转缩放 →
右侧显示：地图 ID、格子数、物件数、**缺失项与原因**（地形未解 / 贴图无路径 / 记录布局未定）。

工作量估计（按"必须验证才写"的规矩）：
1. `.sfl` 语义 —— 中（解码器已有，缺字段含义）
2. `.scene` 记录布局 —— **中大**（757 vs 28×749 的矛盾必须先解开，不能猜）
3. 地图 UI 接入 —— 小（复用现有 WebGL + 状态机 + 缺失原因）

## 7. 架构复用：地图是新的 AssetType，不是新工具

现有链路 `资源文件 → 解析 → 状态 → 展示 → 测试` 全部复用，只在每层加一个类型：

| 层 | 加什么 | 复用什么 |
|---|---|---|
| `crates/core/src/preview/` | `scene.rs`（`.sfl`/`.scene`/`.map` 解析，未知字节如实报告） | JBCF 解码、`MeshGeometry` |
| `crates/core/src/catalog/` | 地图作为一等实体（map_id / 格子数 / 物件数 / 缺失项） | 现有只读 SQL 层 |
| `app/src-tauri/src/` | `map_data(map_id)` IPC | `mesh_view.rs` 的 base64 缓冲契约 |
| `app/web/lib/` | `mapState.js`（沿用 `empty/loading/failed/loaded` 不变式） | `detailState.js`、`seq.js`、`meshLayout.js`、`wording.js` |
| `app/tests/` | 地图状态机 + 记录布局契约测试 | `node --test` 那一套 |

**不要**新写一个地图页面或第二套状态管理——阶段 1 的价值恰恰在于"不会骗人"是结构保证的，
换个页面就得重新犯一遍错。
