# `.pu` 参数块：字段语法的突破口（2026-09-29 晚）

现在工作台/CLI 对 `.pu` 的说法是「材质链、发射器/混合/更新器类名都认得，**参数块字段名未解**，
只报浮点个数」。这份记录写清「未解」解到哪一步了、下一步该往哪打。

样本：`w1351_skill_boss_xiejianling_skill04_chadi.pu`（`data_1` / hash `c7e83e3c089d4515`，
解出 37,736 字节）。取字节：

```bash
.scratch/rc3/debug/examples/dump_raw.exe --root D:/TLGL --pak data_1 \
  --hash c7e83e3c089d4515 --out D:/TLGL/.scratch/raw
```

## 2. 参数区**不用 u32 索引**引用字符串（实测否掉）

把参数区按 4 字节步长扫，找等于 9/10/107/108/164/4/19 的 u32：**一个都没有**（32,231 字节里 0 次）。
所以「参数记录里放 u32 字符串号」这个最自然的猜想不成立。

## 3. 一度以为是线索（u16 连号索引）—— 已实测否掉，别再去走

参数区开头按字节读：

```text
3e 00 05 00 | 01 00 00 00 | 3f 00 01 00 | 00 00 00 40 | 40 00 07 00 | 00 00 00 00
```

按小端 u16 对：`(0x3e=62, 5)`、`(0x3f=63, 1)`、`(0x40=64, 7)` —— 索引**连号**，
而 62/63/64 在表里正好是 `light_2`（实例名）、`wyh_lighting_z019.mtl`（材质）、`Circle`（形状）。
一条发射器记录该有的三样东西齐了，而且顺序合理。中间还夹着 `423c6560` = **46.849** 这个 f32 连出三次
（看着像 Vec3 的缩放或颜色分量）。

**这条是我看十六进制看走眼了。** 那段字节按 4 字节 u32 切是
`3e000500 | 01000000 | 3f000100 | 00000040 | 40000700`：`3f` 落在对齐位上，
`40` 却在一个 u32 的高半区——**步长根本不一致**，「62、63、64 连号」是我把不同对齐的字节
凑出来的。写脚本实测三份文件（`c7e83e3c089d4515` / `a98cce2a2f53259c` / `18e87ec59477f87e`），
按 u16 步长 2 和步长 4 各扫一遍「严格 +1 且长度 ≥3 的游程」：**三份全是 0 个**。

## 4. 现在的诚实状态

已确认的只有两件事：① 字符串表里**有**参数名（`Colour`/`Scale`/`BaseSpeed`/`Gravity`/`Align` 等，
见上面索引表）；② 参数区**不用 u32** 引用字符串号（32,231 字节里 0 次命中）。
语法没解出来，`effect.rs` 与工作台**继续只报浮点个数**，不许把个数当参数值说。
