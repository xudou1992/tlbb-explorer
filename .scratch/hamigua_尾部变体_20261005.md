# hamigua 尾部变体 · 2026-10-05 · 🟢 解出

**结论先行：hamigua 族没有另一套文法。** 它与 10-05 上午解出的条目流
（`crates/core/src/preview/geometry.rs::parse_hierarchy`）共用同一条目语法、
同一套拒绝纪律，差别只有**三个开关**：

1. **无 origin/top 前奏**：整份文件找不到名叫 `origin` 的 96B 记录，尾部直接以
   根条目开始——`[u32 0xFFFFFFFF][名字×2 相同]`（-1 正是根条目标志位）；
2. **挂点数可以为 0**：尾部收在 `[u32 1][u32 0]`（标志 1 + 挂点数 0），
   EOF 分毫不差；旧实现 `count == 0 → None` 把它拒了；
3. **影响顶点表不按排序序存**：顶点号是「绘制序」的排列（相邻成对交换，
   如 `1,0,2,3,…,14,13,…,65,64`），全部互异、全部 < 顶点数；旧判据
   「严格递增」把它拒了。

### 2.3 旧 walker 为什么死在这里

上午的差分脚本只认「96B 记录」当起点。hamigua 全文件只有一条 96B 记录——
0xce4 的 `bone001`，它其实是**根条目孩子名单里的孩子槽**，不是条目开头。
从它起步：把根的孩子槽当成了自己的记录、把条目 2 拼了出来，然后在
0x1094 的 `[1][0]` 上死亡（挂点数 0 被拒）——即使放行，条目数 1 ≠ 声明数 2。
所以上午档案里「无 origin 前奏、末条目无名」两个特征，字节现场修正为：
**前奏缺席（根条目直接 -1 起步）+ 挂点段收在 `[1][0]`；末条目有名**
（`bone001`×2 在 0xda4/0xdc4），「0xde8..0x109c 多出一种 64B 块」就是
已知未证语义的 64B 局部矩阵，不是新块。

### 2.4 第三个开关的发现（差分时差点漏掉）

修掉起点与挂点两处后 hamigua 仍卡在 0xe28——影响顶点表 `[u32 66][顶点×66][权重×66]`
的顶点号**不是严格递增**：`1,0,2,3,…`，尾部 `…63,65,64`。逐号清点 =
{0..65} 每号恰一次（66 个互异值，全部 < 顶点数 66），权重全 1.0。
语义上蒙皮表是「顶点 → (骨，权重)」的映射，顺序本就无谓；排序序只是
xiyuqiezei 一族恰好排了序。判据从「严格递增」放宽为「互异 + 有界」后
（见步骤 4），走通数从 1,439 跳到 2,208——这是三个开关里最大的一把。
