## 2. 记录文法 🟢(7,806/7,806 确定性走通)

```text
参数区 = 头 + 记录流
头     = u32 50, u32 0, u32 K          (K∈0..6,6,324 份为 3;含义🟡)
记录   = u32 key + pw(cls,fld) 个 u32 载荷词
key    = 高16位 cls(载荷类型), 低16位 fld(属性号)
cls=0  → pw=0(无载荷,fld 本身就是值/小整数/索引)
cls=7  → pw=3(三维向量,全类统一)
其它   → 查表(PARAM_PW,326 条,已进 Rust effect.rs)
```

这套文法与 `.sfl`(JBCF)的 `[u32 key=(cls<<16)|fld][pw 个 u32 载荷]` 同构
(`.scratch/sfl_field_map.md` §1 的记录文法),同一引擎的序列化习惯。
9-29 文档观察到的"参数区多是两个 u16 拼的"= key 的 cls/fld 两半;
"前 10 个字段形状两份一致" = 头 + `(1,59)`、`(7,58)` 等开篇记录。

**验证口径是"确定性单向走"**:从起点开始,每条记录按表定宽,不允许任何回溯,
最后一步必须恰好落在参数区末尾。7,806 份全部如此(0 回溯、0 失败)。
这比"存在某种可行切分"强得多——表的每一条都在几百到几十万次出现上无冲突。

方法记录(给下次省时间):
1. 自由 DP 求单文件所有可行切分(位置图可达性,O(n×20));
2. 全库对每个 (cls,fld) 投票出多数 pw,迭代到不动点(2 轮收敛);
3. 失败文件的挂点反推缺失键——教训:**贪心 DFS 早锁错条目会连锁污染**;
   cls=0/7 必须先锁类硬规则,否则零串上的伪边会把表拖进震荡
   (发生过 96.9%↔68% 的来回翻)。

## 4. fld 命名到哪一步 🟡

fld 是**类型内的属性号**,跨文件稳定(同 key 在所有文件里宽度一致、
载荷值域一致)。命名要靠 exe 侧的属性读写表(9-29 文档方向 3)或
"属性名→id"的锚定。目前只有两个键有语义证据(§5),其余只报
(cls,fld,值)。**没有把猜测当结论写进任何口径。**

已证伪 🔴:「fld = 字符串索引」。大文件 xiejianling_skill04_chadi 的参数区开头
`(5,62),(1,63),(7,64)` 恰好撞上 str[62]='light_2'、str[63]='wyh_lighting_z019.mtl'、
str[64]='Circle'(9-29 文档"连号索引"的残余形态),但 `(7,64)` 全库出现 877 次,
而绝大多数文件字符串不足 64 条——同一键不可能一半文件可索引一半越界。
**属性号与字符串号是两套空间,大文件纯属巧合。**

另:头部第三词 K 与该文件 (5,62)(疑似 technique 节)出现次数**无对应**
((K=4,n=0) 有 236 份、(K=3,n=1) 有 6,323 份)——K 的含义🟡未定,别再拿它当节计数。
