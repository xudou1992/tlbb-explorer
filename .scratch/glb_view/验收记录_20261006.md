# 蒙皮导出人眼验收（2026-10-06 上午）

**验的是什么**：`.scratch/glb_rigged/` 两份带骨架/蒙皮/动画的 `.glb`。上一班（v0.5.0 三个 agent）
留下的欠账是「B 的矩阵换算只验了结构一致性，没进查看器用眼睛看过」。这次补上。

## 方法（不用自研查看器，不用自吃闸门）

- 查看器：**three.js r169 的 GLTFLoader**（`web-viewer/node_modules/three`，业界实现，
  蒙皮与动画由它按 glTF 规范自己算）+ 一个 60 行的取片页面 `.scratch/glb_view/viewer.html`。
- 取片：本机 Chrome headless（独立 `--user-data-dir`）+ CDP `Page.captureScreenshot`。
  Qoder 内置浏览器没有可见视口（`viewport=0x0`），截不到图，所以走这条。
- 校验器：**Khronos 官方 gltf-validator 2.0.0-dev.3.10**（npm 包，装在
  `.scratch/glbcheck/node_modules`，只读产物）。

## 一、官方校验器：改前 8,245 个 error，改后 0

| | 改前 | 改后 |
|---|---|---|
| yifu_001 | **8,245 error** / 52 warning / 1 info | **0 / 0 / 1** |
| shoutao_001 | **8,131 error** / 0 / 1 | **0 / 0 / 1** |

四把根因（都不是结构问题，是自吃闸门看不见的那一类）：

1. `push_f32` 给每个 bufferView 无差别打 `target=ARRAY_BUFFER` → IBM 与动画数据的 view
   被判 `BUFFER_VIEW_TARGET_OVERRIDE`（一份文件 6,076 个）。
2. animation sampler 的 input accessor 的 min/max 写成**标量**而非数组 → 30 个 `TYPE_MISMATCH`
   + 2,025 个「没有边界」（每个引用它的 sampler 报一个）。
3. glTF **硬要求**每顶点权重和为 1.0，旧口径「Σw 对不上就照原样写」→ 114 个
   `ACCESSOR_WEIGHTS_NON_NORMALIZED`。
4. 权重 0 的槽位还挂着非零骨号 → 52 个 `ACCESSOR_JOINTS_USED_ZERO_WEIGHT`。

剩下的 1 个 info 是 `UNUSED_OBJECT`（TEXCOORD_0 导了但没导图），诚实：材质是中性灰。

## 二、画面：bind 姿态是对的，动画是坏的，坏因看得见

- `a_bind_front.png`——**不播动画**时，781 顶点是一份完整站立的武僧：头与帽、躯干、
  双臂、双腿、右手弯刀俱全，立在 y 0.019..2.240。**几何、IBM、node 局部 TRS、
  行列式约定全部读得通**（行向量→列向量那套换算到此为止是干净的）。
- `b_bind_bones_front.png`——同机位叠加骨架：**46 根骨躺在地上**，贴着 y≈0 的水平面
  朝右侧摊开，与站立的网格完全对不上。这就是 pose.rs 记档的开口第一条
  （骨平移 y∈−0.16..0.78、多数≈0，骨沿 z 拉开；骨位与蒙皮重心平均偏 1.84）
  的**可视化证据**。
- `e_idle01_t5.png`——播 idle01 第 20 帧：模型被撕成尖刺（头还在原位，弯刀整块飞到左侧，
  躯干与裙甲拉成细长条）。这不是「刚体摆歪」，是不同顶点跟着落在不同位置的骨走。
- `f_run_t3.png`、`d_idle01_t5_bones.png` 同形。

**判定：姿势怪 = 数据口径，不是导出 bug**（与上一班报告的预判一致，且这次有画面）。
数学侧已经排除了两种嫌疑：① 乘序——单骨权重 1 的顶点到骨原点距离在 555 帧里守恒，
最大相对违例 1.05e-6，倒序则违例 19.03；② 约定换算——规范侧独立实现与 pose.rs
逐元素相等（bind 6.3e-7、逐帧动画 0e0、蒙皮 7.1e-7）。
剩下的唯一解释是**骨数据空间与网格空间之间差一个全局轴变换**，正在量：
`.scratch/axis_probe/`（Kabsch 拟合骨原点 → 蒙皮重心）。

## 三、两份样品的真实身份（别拿错）

- `m_db18794d0000cd38.glb`（yifu_001，781 顶点）：**唯一真蒙皮样品**，529 个顶点带真实权重
  （441 个 Σw 严格 1.0 + 88 个差额挂根骨），252 个只挂在根骨上。
- `m_8ff895cd00003a5c.glb`（shoutao_001，42 顶点）：**蒙皮覆盖 0 个顶点**（extras 里
  `coveredVertices: 0`），42 个顶点整份权重挂根骨 → 它在查看器里**永远不会变形**。
  报告说「两份都带 15 条动作」在文件层面成立，但它演示不了蒙皮，验收别看它。

## 四、顺带查出的两条数据事实

1. 主样本 675 条 rotation 轨道、24,300 对相邻关键帧里有 **86 对反号**（最小点积 −1.0000001）。
   q 与 −q 是同一个旋转，但 glTF 的 `LINEAR` 是归一化线性插值，反号会在中点算出零四元数
   → NaN。导出侧现在按帧定半球（`same_hemisphere`），不改任何旋转。
2. 555 个「带表顶点」里有 **26 个的表项权重全是 0**，剔除 0 权重后它们等同于未覆盖。
   覆盖数从 555 改成 529 + 26 就是这个口径差，锚点已写进闸门。
