# `.pu` 参数块：字段语法的突破口（2026-09-29 晚）

现在工作台/CLI 对 `.pu` 的说法是「材质链、发射器/混合/更新器类名都认得，**参数块字段名未解**，
只报浮点个数」。这份记录写清「未解」解到哪一步了、下一步该往哪打。

样本：`w1351_skill_boss_xiejianling_skill04_chadi.pu`（`data_1` / hash `c7e83e3c089d4515`，
解出 37,736 字节）。取字节：

```bash
.scratch/rc3/debug/examples/dump_raw.exe --root D:/TLGL --pak data_1 \
  --hash c7e83e3c089d4515 --out D:/TLGL/.scratch/raw
```

## 2. 参数区**不用 u32 索引**引用字符串（实测否掉）

把参数区按 4 字节步长扫，找等于 9/10/107/108/164/4/19 的 u32：**一个都没有**（32,231 字节里 0 次）。
所以「参数记录里放 u32 字符串号」这个最自然的猜想不成立。

## 3. 一度以为是线索（u16 连号索引）—— 已实测否掉，别再去走

参数区开头按字节读：

```text
3e 00 05 00 | 01 00 00 00 | 3f 00 01 00 | 00 00 00 40 | 40 00 07 00 | 00 00 00 00
```

按小端 u16 对：`(0x3e=62, 5)`、`(0x3f=63, 1)`、`(0x40=64, 7)` —— 索引**连号**，
而 62/63/64 在表里正好是 `light_2`（实例名）、`wyh_lighting_z019.mtl`（材质）、`Circle`（形状）。
一条发射器记录该有的三样东西齐了，而且顺序合理。中间还夹着 `423c6560` = **46.849** 这个 f32 连出三次
（看着像 Vec3 的缩放或颜色分量）。

**这条是我看十六进制看走眼了。** 那段字节按 4 字节 u32 切是
`3e000500 | 01000000 | 3f000100 | 00000040 | 40000700`：`3f` 落在对齐位上，
`40` 却在一个 u32 的高半区——**步长根本不一致**，「62、63、64 连号」是我把不同对齐的字节
凑出来的。写脚本实测三份文件（`c7e83e3c089d4515` / `a98cce2a2f53259c` / `18e87ec59477f87e`），
按 u16 步长 2 和步长 4 各扫一遍「严格 +1 且长度 ≥3 的游程」：**三份全是 0 个**。

## 4. 现在的诚实状态

已确认的只有两件事：① 字符串表里**有**参数名（`Colour`/`Scale`/`BaseSpeed`/`Gravity`/`Align` 等，
见上面索引表）；② 参数区**不用 u32** 引用字符串号（32,231 字节里 0 次命中）。
语法没解出来，`effect.rs` 与工作台**继续只报浮点个数**，不许把个数当参数值说。

## 5. 下次值得试的方向（都还没试）

1. **对齐方式**：u16 索引若存在，步长可能是 6 或 8（索引 + 类型 + 值），先按「同一文件里
   反复出现的固定步长」找周期，而不是猜步长；
2. **拿最小的 `.pu` 反推**：几百字节的特效只有一条发射器，参数区小到可以逐字节读完，
   比在这份 37KB 的怪物上找规律快得多——下次从 `stored` 最小的十几份开始；
3. **exe 侧的序列化代码**（要 IDA 会话，本机没起）：类名 `Emitter`/`Affector`/`Component`
   在二进制里必然有对应的读写函数，一次能定死整块布局。

没写解析器、没改 `effect.rs`、没动界面文案——只有结构证据、没有可验证的语法，就不改口径。

## 6. 最小样本读下来的原始观察（2026-09-29 晚，未成语法）

按文档里第 5 节的第 2 条做了：取两份最小的 `.pu`（各 360 字节、字符串 7 条、参数区 208~220 字节）
`2f53979d76ef7484`（`data3`）与 `85e96560512362ea`（`data_1`），逐 u32 打完一遍。

关键形状——**参数区里的 u32 大多是两个 u16 拼的**，而且低半区小、高半区是 1/3/5/7 这种小数：

| u32 十进制 | 拆成 (低 u16, 高 u16) | 旁边 |
|---|---|---|
| 65609 | (9, 1) | 后面紧跟 f32 0.1928 |
| 65610 | (10, 1) | 后面紧跟 f32 0.1928 |
| 65611 | (11, 1) | 后面紧跟 f32 0.1928 |
| 65595 | (27, 1) | |
| 458810 | (58, 7) | |
| 327742 | (62, 5) | |
| 196675 | (67, 3) | |
| 721100 | (172, 11) | |
| 1008981770 | — | 就是 f32 **0.01**，连出四次 |
| 1120403456 | — | f32 **100.0** |

三条读法：

1. `(9,1) f32 / (10,1) f32 / (11,1) f32` 这种**低半区连号 + 高半区恒 1 + 各带一个 f32**，
   看着像「序号 + 类型 + 值」的定长属性项；同一份文件里 9/10/11 在**大**文件的字符串表里
   正好是 `Colour`/`Scale`/`dyn_curved_linear`——但小文件只有 7 条字符串，**索引越界**，
   所以低半区到底是字符串号还是属性序号，这两份样本分不开，别急着定。
2. 0.01 连出四次、100.0 单独出现——与 `.mesh`/`.ani` 里那套 ≈1/100 的单位换算对得上味，但同样未证。
3. 参数区开头在两份文件里都是 `50, 0, 3(add/mtl名), 65595, 0.01, 458810, 0.01, 0.01, 0.01, 327742`
   —— **前 10 个字段的形状两份一致**，说明头部是定长小节，不是变长字符串流。

要定语法还缺：一份「字符串条数 > 20 且参数区 < 400 字节」的样本（现在这两份字符串太少、
大文件参数区又太大），以及同一属性在多份文件里的偏移一致性统计。这活不小，留给下次。
