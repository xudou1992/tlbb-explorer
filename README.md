## 这是什么

一个只读的客户端资源浏览器/解包预览器。**不做资产知识图谱**，只回答
「客户端里有什么、长什么样」。

**第一屏是「浏览」（2026-09-27 用户定版）**：左边点一个 `data*.pak` → 中间列出
它里面的文件夹结构（原始路径树）→ 点文件预览（贴图直接出大图）→ 一键导出
（单文件 / 文件夹 / 整包，目标目录强制在客户端根之外）。没有名字的文件按
16 位编号摆在「(未命名)」桶里，照样能预览能导出——编号是身份不是路径，不编造。

其余入口都是第二位：

- **资产检索**（第二标签）：按「资产组」搜索与详读，面向研究
- **分析模式**（开发者选项）：refs / dangling / evidence

### v0.4.5 蒙皮权重正名 + 材质页（2026-09-30）

**权重这条翻了案**。此前写着「蒙皮权重不在 `.mesh`，也不在 `.ske`」，那是按
「每顶点 4 影响、Σ=1 的**定长表**」穷举出来的结论——那种编码确实不存在，
但权重本身在：每条 96B 骨记录之后紧跟 `[u32 顶点数 N][N 个顶点号（互异且有界，**不保证递增**）][N 个权重 f32]`，
是**按骨组织的影响顶点表**。
> **2026-10-12 就地改掉一处事实错误**：这句原先写着顶点号「**严格递增**」，那是当时的老判据，
> 而它把按绘制序存表那一族**整族判成没有权重**（实测误杀 126/468 份）。判据换成「互异 + 有界」后，
> 全库带表文件 2,090 → 2,227 份，另修掉 `parse_nodes` 少扫 2 相位的漏判。
> 顶点号两种存法都真实存在，这条是实测不是推测（证据与闸门见 `.scratch/cfg身份普查_20261011.md`）。
样本 `w1351_monster_xiyuqiezei_yifu_001.mesh`（781 顶点）：
32 条节点记录里 26 根带表，覆盖 555 个顶点，每顶点被 1~3 根骨影响，
**按骨累加后 441 个顶点的权重和正好 1.0**。口径在 `preview::SkinInfluence`，
闸门 `skin_influences_sum_to_one_per_vertex`（逐顶点和 ≈1）+ 两条反向验红
（改一个权重越界 / 打乱一次顶点号 → 整张表不认）。
**带不带表按份算**：同一只怪 `yifu_001` 26 根、`shoutao_001` 0 根，
所以骨架页加了「看哪份网格」的选择条与「影响顶点」列。

**材质页**：全库 8,536 份 `.mtl` 是 JBCF 配置容器，`view.exe` 早就打得出一张
「槽位 / 客户端原文 / 对不对得上实体」的表，工作台上却只有两行字。
现在详情第十个标签「材质」列这张表，对不上的写「缺」并说明是客户端的设计。
只认组内登记的定义文件（与特效页同一道归属闸门：400 组逐个核）。
**骨架页的骨表按 `.ani` 轨道名单铺全**：这具骨架声明 46 根、`.mesh` 只给 32 条矩阵，
以前界面上只列 32 行再用一句话解释差额；现在 46 根一根不少（骨序按 `.ani` 排，
`origin`/`top` 这类没有动画轨道的框架骨排在后面），没矩阵的那些行写
「矩阵不在 .mesh 里」，不编坐标也不留空行。

**`.mdl`（2,146 份模型定义）也走这一页**——因为一批 NPC/怪物组的**本名其实是 `.mdl`**，
只列 `.mtl` 等于把本名那份漏掉；`.mdl` 回的是「骨架 + 网格·材质对 + 其他名字」，
段名（LOD / `MainBodyMesh`）跟着每一对走，不然多组时分不清谁是谁。

**筹码区加了上限（24 颗）**：验 `.mdl` 时撞出来的一屏事故——有个组名下登记了
**838 份定义**（就是那个 3,405 成员的巨无霸组），筹码把整排铺下去之后
**要看的表被挤出了屏幕**，等于换了个地方看不见。现在最多摆 24 颗，且**这句说明自己就能点**：点一次再摆 100 颗、剩下的数跟着减
（真窗口实测 24 → 124，说明从「还有 815 项」变成「还有 715 项」，要看的表一直留在屏幕里）。
原先写的是「还有 N 项没列出（在「组成成员」里能看全）」——去核了一遍，
那一栏是关系图 + 分类计数，**没有全量名单**，那句话是指路给一个不存在的地方；
真能看全的是「文件清单」（实测这一组 3,405 条列得全）。**当前选中的那颗一定摆进来**，

**关于「动画 / 着色器还没搞定」的口径**（动画部分 2026-09-29 更新）：

- **骨骼动画**：`.ani` **关键帧已解出**（v0.5.0 的解析层）——每骨每帧
  四元数 + 位移 + 缩放，四个真样本 21/26/31/41 帧逐字节对齐、全部四元数单位长，
  口径钉在 `crates/core/src/preview/anim.rs`，并由一条全库抽样闸门守着：随机抽
  60 份 `.ani`（骨骼数 1~181）→ 230,268 个旋转字段全部单位四元数。**父骨链已解出**
  （2026-10-05，`.mesh` 尾部孩子名单的并，见上），蒙皮权重也在 `.mesh` 里按骨组织
  （2026-09-30）。复合数学层 `preview::pose` 与 GLB 蒙皮/动画导出
  `export::gltf::to_glb_rigged` 同日落了码。
  **播放仍未上屏**，但卡点在 10-06 上午换了一次：原以为「bind 骨架与网格世界不重合」
  是一处轴系开口，实测**翻案**——`.mesh` 里存的 96B 矩阵是**世界绑定矩阵的逆**
  （`B = S⁻¹`，即 glTF 的 inverseBindMatrix、D3DX 的 bone offset），根本不是轴系问题。
  判据是物理的、不依赖任何既有结论：骨位应贴着它蒙皮顶点的加权重心——现口径
  mean **0.1488**，把存储值直接当骨位是 **1.4393**；父子骨原点距离也从 0.000~3.180
  回到 0.000~1.099 的骨长量级，脚趾 y=0.140、脚踝 0.693、胸口 1.270 全是站立的解剖

## 首次运行（换机后）

### 1. 自备客户端

仓库不含客户端。需要一份 TLBB 客户端安装，其中至少有：

```
<客户端根>/
├── data.pak data1.pak ... data4.pak data_1.pak    # 资源容器（6GB）
└── ...（其余运行文件）
```

### 2. 重建资源清单

`resources.db`（145MB）不入库，需要重新索引客户端。建库脚本随仓库分发在
`.scratch/dbbuild.py`（Python + 标准库 sqlite3，无第三方依赖）。三步有先后顺序，不能并成一步：

```bash
# 第 1 步：扫 6 个 pak 的索引 → resources / records（顺带落 .scratch/index_off.tsv）
python .scratch/dbbuild.py
# 第 2 步：把 payload 解出来（refs / relations 要从文件内容里读，见下方说明）
python .scratch/pakunpack2.py --outdir <客户端根>/.scratch/out
# 第 3 步：读 JBCF 字符串表建引用边、聚资产图
python .scratch/dbbuild.py --no-build --rels --assets --extras
```

客户端不在 `D:\TLGL`、或库想建到别处，用命令行或环境变量覆盖（与 Rust 侧同一套约定）：

```bash
python .scratch/dbbuild.py --root E:/Games/TLBB --db E:/Games/TLBB/.scratch/resources.db
# 等价：TLBB_ROOT=... TLBB_DB=... python .scratch/dbbuild.py
```

> **`--rels` 那一步的产出取决于第 2 步解没解全。** 引用边（`refs`）不是从文件名猜的，
> 是打开材质/骨架/模型这些 JBCF 文件的字符串表读出来的，所以它只认
> `.scratch/out/all/<容器>/<编号>…` 里真存在的字节。本机实测：只跑第 1、3 步
> （`out/all` 不全）得到 `refs` 93,395 / 资产组 12,779；把 payload 解全之后才是
> 基线那套 98,504 / 13,080。**别拿一个没解全的库去对基线然后说脚本错了。**

> 名字表来自 `.scratch/names_jrpc.tsv`（JRPC 恢复出来的 hash→虚拟路径，随仓库分发）。
> 没有它照样建库，只是绝大多数条目会落到「未命名」那一边——那是客户端打包时
> 剥掉文件名的结果，不是解析漏了。

建完后**务必跑基线核对**（等级分布是冻结值）：

```bash
cargo run --release --bin catalog_baseline
# 期望（对应随仓库分发那份库）：A20 / B2581 / C10479 / D0
# 组 13080 / 成员 48122 / 资源 105327
# 用修好走链的脚本重建会得到 资源 107126（多 1,799 条）——那 1,799 条是
# data_1.pak 第 12、13 两代索引里的真文件，老库没跟到链。基线常量尚未重钉
# （重钉要连库一起换，属于口径变更），在此之前对不上是已知状态，见下一段。
```

对不上就说明索引方式和当初不同，**先查清楚再继续**，不要改冻结值。

> **2026-09-29 实测：照上面重建，数字会比冻结基线多 1,799 条（107,126 vs 105,327），
> 这不是重建错了，是随仓库那份库少算了。** 差全部来自 `data_1.pak`（更新器写的补丁包）
> 的第 12、13 两代索引数组：老库只跟到第 11 代，而新库是老库的严格超集（老库独有的
> hash 有 0 个）。根因是建库脚本的索引遍历靠「上一条 payload 的末尾」猜下一个数组位置，
> 补丁包的数组不连着排就断了链——已改成与 Rust `jpak` 同一口径顺着数组头里的 `next`
> 指针走（`.scratch/pakunpack2.py`），改完 Python 侧与 Rust 侧一字不差：
> `data.pak` 16 数组 / 15,651 槽，`data_1.pak` 14 数组 / 13,684 槽。
> **基线常量还没重钉**（那要连随仓库那份库一起换，属于口径变更），在此之前
> 重建后跑 `catalog_baseline` 必然对不上，原因就在这段话里。

`.mesh` 有多个子网格（先锋衣服 5 段、`ysym_moren` 6 段），旧代码把基础色图绑给整只网格，

- **同日追加：拿撕边数重扫 48 个全局轴置换**（`stretch_probe --rsweep`）。
  10-06 用位移扫判「R 不唯一」，这次尺子对全局刚体不变、只对骨间相对错位敏感：
  **恒等轴系在 idle01 排第 47/48**（撕边合计 2,959），最好的 `(2,1,0)(+,-,+)`
  降到 810（**3.7 倍改善**）但仍拉到 4.07 倍；冠军逐动作漂移
  （walk `(2,1,0)(-,-,-)`、run `(0,1,2)(+,-,-)`）⇒「R 不唯一」在新尺子下依然成立，
  可三条的前三名**全部 y 轴取负**——手性/上方向差一个 Y 翻转是真的，
  剩下的错位不是全局置换能表达的。收窄成两条：逐骨轴（10-06 只按 frame0 判过失败，
  从没按撕边判过）、或回 exe 读求值函数。

人眼验收（重建 exe 开工作台：动作页拖帧/播放/换件/整组勾选）仍是用户点头前的欠账——
「解出来了」≠「界面上能看见」，测试绿不替用户点头。

已解：`.ani` 的关键帧（每骨每帧 旋转/位移/缩放）与骨架静态区的绑定旋转，
口径与证据在 `crates/core/src/preview/anim.rs`。浏览视图点一条 `.ani` 会报
「骨骼 N 条 · 关键帧 M 帧 · 会动的骨 K 根」，并写明为什么还不能播。

**骨架的绑定姿态已经有了**（2026-09-29 晚间纠正了当天下午的口径）：`.mesh` 尾部
一条记录 96 字节 = 名字 `char[32]` + 矩阵 `f32[16]`，矩阵是引擎那套 **D3DX 行向量**
约定——前三行基向量，**末行 `(tx,ty,tz,1)` 就是绑定位移**。当天下午写的「末行恒
0,0,0,1」只对单位矩阵成立，害得 46 根骨的怪只认出 2 条记录；判据改对后同一份文件
认出 **32 条**（2026-09-30 又排掉 4 条假骨：挂点表 128B = `tx_*` 挂点名 + 骨名 + 矩阵，
  第二段也是「名字 + 矩阵」，`Bip01_Head`/`Bone01`/`Bip01_Spine1`/`Bip01_Spine` 就是这么混进来的——
  它们是挂点指向的骨名大写别名，不是多出来的四根骨）。四条外部对账都成了闸门：左右同名骨只差一根轴的符号（5 对全中）、
头部 `0x110` 的 u32 = 骨骼根数且等于同组 `.ani` 的轨道数（46==46）、改一个平移
镜像对立刻断（反证）。文件末尾另有一张 **挂点表**（`tx_*` 名 + 骨名 + 矩阵；
10-05 钉成 `[u32 4]` + 4×128B，见下），与骨架不同源。

**数据出得去**：`cargo run --offline --bin skel_dump -- --name <模型或组干名>` 出一份
JSON——骨架节点（含绑定位移）+ 该模型全部动作的关键帧。实测 `w1351_monster_xiyuqiezei`：
15 条动作 × 46 骨、声明 46 根骨、节点 32 条，8.0 MB。没解出来的东西写在文件自己的
`missing` 字段里，每条布局的出处写在 `provenance` 里，拿到的人不必猜少了什么。

**父骨链已解出（2026-10-05）**：`.mesh` 尾部那 10 根「只有名字」的骨不是坏数据，
整段尾部是一条**条目流**——每条 = 可选 96B 绑定记录 + 若干数据块 +
`[u32 标志][名字×2][u32 孩子数][孩子名单]`。骨名前那个 u32 是**标志位**
（非根恒 1、根为 −1），9-30 线索里「值像父索引」是巧合对了两根——47 份、
33 种骨数（14~128）的差分里无一例外是 1/−1，**「父索引字段」不存在，别再找**。
孩子槽要么是 32B 名字（无绑定矩阵的骨），要么整条 96B 记录（名字段共用字节）；
把全部条目的孩子名单收并起来，除根外每根骨**恰好被列一次**——父链就是这张名单的并。
证据三道：① 47 份差分全部「整文件走到 EOF 分毫不差 + 条目数 = 0x110 声明数」；
② 解出的链与标准 Biped 解剖逐骨一致（thigh→calf→foot→toe0、
clavicle→upperarm→forearm→hand、spine→spine1→neck→head）；③ 几何对账——
17/20 对「父子都有矩阵」的位移差落在骨长区间，09-29 手算的 1.0991 / 0.4052 /
0.5460 三个距离逐对复现（当时那份「距离像骨长」的表，骨对就是这条链）。
尾部最后一段也钉死了：`[u32 4]` + 4×128B 挂点表（`tx_head`→`Bip01_Head` 等）。
口径在 `geometry.rs::parse_hierarchy`（孩子名对不上/被列两次/多根/有环/
条目数≠声明 → 整体 None，不猜），闸门 `crates/core/tests/bone_hierarchy.rs`
六条全绿；证据档案 `.scratch/父骨链_验证_20261005.md`。

**播放的三个输入至此齐了**：`.ani` 局部位姿 + 父链 + 绑定矩阵。下一步是复合：
按行向量约定 `world = local · parent_world`，无矩阵的骨沿父链推。
两个新开口记在档案里：64B 局部矩阵与 88B 对角块的语义（八种复合口径全对不上
bind，残差 2.3~4.8，只识别未解释）；hamigua 族尾部变体（无 origin 前奏、
末条目无名，抽样里 634/681 未走通的主来源）。此前拿证据排掉的去处仍是史实，
别再走一遍：`.ske` 是动作登记表（数值区几乎全零）；客户端 exe 里 `bip01`
出现 0 次；父索引不是裸 u32 数组；`.ani` 骨架区 `+48` 不是绑定位移。

**复合的账：一个「模型」从来不是一件（2026-10-05 实测，用户看素材时点破的）**

用户问「好多素材是不是要拼接起来」——对，这笔账就是 v0.5.0 播放复合的工作量清单。
实测口径：解包树里特效/场景那一片（`.scratch/unpacked`，1,441 份 `.mesh`；全库数字
只会更大，规律一致）：

- **多件套是常态**：1,441 份 `.mesh` 按名字归组，**142 组是多件套、盖住 525 份
  （36%）**。瀑布 `w1351_model_pubu` 拆成 25 块（`_h001`/`_s001`…），女明教一套
  14 块（`_x05`…）——单块看不出是什么，摆到一起才是完整的水面/人物。
- **动画天生是外挂的**：442 副骨架对 3,822 份 `.ani`，平均一副骨架挂 9 个动作，
  全要靠骨架绑到 mesh 上才动得起来。
- **最小完整件**：西域窃贼 = 1 mesh + 1 `.ske`（动作登记表）+ 5 `.ani`
  （idle/walk/run/behit），三样拼一起才是一只活怪。
- 已经拼完的两层：**场景层**（摆放记录 × mesh，全量 28.5 万条实例，v0.3.2 闭环）、
  **材质层**（mesh→`.mtl`→贴图，v0.3.0 闭环）。
- 没拼完的一层就是 v0.5.0 本身：**mesh + 骨架 + 动画 + 权重 → 一个能摆姿势的整体**。

### 地图侧已锁的口径（v0.2/v0.3 的成果，别再回头验）

`.scene` 格式**已解**（全量 11,933 文件独立复算）：

```text
偏移 0x00  u32  n_records    记录数（★会被低估，尾部还有附加段）
偏移 0x04  u32  tag          753 / 749 / 605 / 592 / 596 / 601 / 324 / 957
偏移 0x08  u32  zero

base   = 12        恒定，与 tag 无关
stride = tag + 8   753→761、749→757、605→613、592→600
记录   := [64B 列主序仿射矩阵] [名字区，长度 = stride-64，名字起点恒为 64]
平移在 m[12], m[13], m[14]；floor(m[12]/32)、floor(m[14]/32) 对上格子文件名
```

`node tools/map_golden.mjs` 的 6 张真图金标准盯着。

## 已知的环境陷阱（Windows 沙箱）

1. **PowerShell 仍是抓输出的主力** —— 控制台是 cp936，Python 直接打印中文会成乱码；把结果写进 `.txt` 或文件再读。Git Bash 可用，但传参里的反斜杠会被吃掉，路径一律写正斜杠。
2. **PowerShell 吞 stdout**，`*>` 产出 UTF-16LE。抓输出要写 UTF-8 文件再读。
3. **判断命令成功只看 `$LASTEXITCODE`** —— `NativeCommandError` 是假警报。
4. **构建必须** `CARGO_TARGET_DIR=D:\TLGL\.scratch\rc3` + `--jobs 1`。
5. **同文件多处编辑禁止放同一条消息**（读旧写回会互相覆盖）。
6. `crates/core` 无 `anyhow` / `image` 依赖（离线环境），新代码只用 `std`。
